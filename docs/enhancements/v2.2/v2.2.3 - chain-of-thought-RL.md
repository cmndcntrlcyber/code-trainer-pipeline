# v2.2.3 Chain-of-Thought Reinforcement Learning

**Status:** Infrastructure complete (scripts, reward function, session ingestion implemented)  
**Phase:** 4c (post-SFT, pre-GGUF)  
**Hardware:** HF Jobs A100-large (80 GB)  
**Base model:** Qwen2.5-Coder-14B-Instruct + V9 SFT adapter

---

## Summary

Phase 4c adds a two-stage reinforcement learning pipeline between SFT (Phase 4) and GGUF conversion (Phase 5) to fix V9's tool_call tag emission failures and improve multi-step reasoning quality. Stage 1 uses GRPO (Group Relative Policy Optimization) with a rule-based reward function to enforce structural correctness of tool calls. Stage 2 uses DPO (Direct Preference Optimization) with preference pairs derived from OCO sessions — HTB, THM, bug bounty, Claude (positives) versus V9 inference failures (negatives) to improve agent reasoning chains.

```
Phase 4 (SFT)
  V9 adapter
    |
    v
Phase 4c Stage 1: GRPO
  rule-based reward (tool_call_reward.py)
  fixes: tag emission, tool name accuracy, clean termination
    |
    v
Phase 4c Stage 2: DPO
  preference pairs from OCO ground truth
  fixes: multi-step reasoning, hallucination, chain-of-thought quality
    |
    v
Phase 5 (GGUF conversion)
  V10 adapter
```

---

## Problem Statement

The V9 SFT model (trained on the V9 mixed dataset with curriculum training) exhibits three categories of failure when deployed through the V10 nexus-harness evaluation:

### 1. Tool call tag emission failures

The model generates syntactically correct JSON tool calls but intermittently omits the required `<tool_call>` / `</tool_call>` wrapper tags. Without these tags, the tool-calling middleware cannot parse the model's intent and the agent loop stalls.

**Example failure:**
```
# V9 output (broken):
{"name": "bash", "arguments": {"command": "nmap -sV 10.10.10.1"}}

# Expected output:
<tool_call>
{"name": "bash", "arguments": {"command": "nmap -sV 10.10.10.1"}}
</tool_call>
```

### 2. Multilingual garbage appended to outputs

After generating a valid tool call or reasoning block, the model sometimes appends tokens from non-English languages (Chinese, Korean, Arabic) -- residual activation patterns from the Qwen base model's multilingual pretraining data. This corrupts the output and breaks downstream parsing.

### 3. Failure to reason step-by-step

When faced with multi-step offensive security tasks (e.g., enumerate -> exploit -> escalate), the model jumps directly to exploitation without first running reconnaissance, or produces single-step plans that miss critical intermediate steps. SFT alone does not teach the model to decompose problems into sequential sub-goals.

## Architecture

### Pipeline Position

Phase 4c sits between Phase 4 (SFT) and Phase 5 (GGUF conversion) in the RTPI training pipeline:

```
Base Model
  |
  v
Phase 3b: DAPT (domain-adaptive continued pretraining)
  |
  v
Phase 4: SFT (supervised fine-tuning on V9 mixed dataset)
  |
  v
Phase 4c: Chain-of-Thought RL        <--- THIS DOCUMENT
  |-- Stage 1: GRPO (structural correctness)
  |-- Stage 2: DPO (reasoning quality)
  |
  v
Phase 4e: RLAIF (reward modeling)
  |
  v
Phase 4f: PPO (RL fine-tuning with learned reward)
  |
  v
Phase 5: GGUF conversion + deployment
```

### Stage 1: GRPO (Group Relative Policy Optimization)

GRPO generates multiple candidate completions per prompt (num_generations=4), scores each with a deterministic rule-based reward function, and uses the relative ranking within each group to compute advantages. This avoids the need for a separately trained reward model or value network.

**Reward function:** `tool_call_reward.py` (5-component scoring)

**Training data:** V10 eval prompts -- the same nexus-harness tool-use scenarios that the model will be evaluated against.

### Stage 2: DPO (Direct Preference Optimization)

DPO directly optimizes the policy using preference pairs without a reward model. Each pair consists of:
- **Chosen (positive):** A successful multi-step reasoning trace from a completed HTB/TryHackMe room
- **Rejected (negative):** The V9 model's failed attempt at the same or similar scenario

The implicit reward learned by DPO captures reasoning quality, chain-of-thought coherence, and agent progress -- properties that are difficult to specify as rules.

## Data Collection

### Quick start — prepare the training host and publish edge scripts

From the project root (`/mnt/ssd/training/`):

```bash
mkdir -p data/cot_rl_sessions/{htb,thm,claude,bugbounty} data/oco_converted data/rl_data/{positives,negatives} && for s in scripts/{edge_push,bootstrap_edge_sync,sync_sessions_to_r2,sync_config}.sh; do (cd /tmp && wrangler r2 object put "cot-sessions/_scripts/$(basename "$s")" --file "$OLDPWD/$s" --remote) && echo "PUT $s"; done && bash scripts/pull_sessions_from_r2.sh
```

This does three things:
1. Creates all intake directories the pipeline expects (`htb`, `thm`, `claude`, `bugbounty` sources plus output dirs)
2. Pushes edge sync scripts to `r2:cot-sessions/_scripts/` so edge devices can pull them without cloning the repo
3. Pulls any sessions already synced from edge devices via R2

Re-run `bash scripts/pull_sessions_from_r2.sh` anytime to fetch new sessions.

### Push sessions from edge devices (Kali Docker containers)

Edge devices are bare Kali containers with no repo, no Node.js, no wrangler.
`scripts/edge_push.sh` is a self-contained pusher that uses only `curl` + `bash`
(both standard on Kali). It uploads `~/.claude/projects/**/*.jsonl` to R2 via the
Cloudflare API, with mtime-based dedup and automatic exclusion of sensitive files

### Negative examples (V9 failures)

Run the V9 model through all V10 evaluation scenarios and collect outputs that fail any of:
- Tool call tag validation (missing `<tool_call>` wrapper)
- Agent progress threshold (fewer than 5/7 steps completed)
- Clean termination (output contains multilingual garbage or truncated JSON)

```bash
# Collect V9 failures on V10 eval scenarios
python -m src.phase4c_rl.scripts.collect_negatives \
    --config src/config/config.yaml \
    --model-adapter ${HF_USERNAME}/qwen14b-code-trainer-v9_mixed \
    --output-dir data/rl_data/negatives
```

Expected yield: 200-500 failed trajectories from 14 tool_call scenarios and 7 agent scenarios.

### Positive examples (OCO ground truth — HTB, THM, bug bounty, Claude sessions)

User-provided session histories from completed offensive cyber operations serve as ground-truth positive examples. Sources include HackTheBox rooms, TryHackMe rooms, bug bounty program sessions, and Claude session histories. These are real pentest/security sessions where a human successfully completed the reconnaissance -> exploitation -> privilege escalation chain, providing the model with examples of correct multi-step reasoning.

**Session ingestion pipeline:**

```bash
# Ingest raw HTB/THM session logs
python -m src.phase4c_rl.scripts.ingest_oco_sessions \
    --input-dir data/cot_rl_sessions/ \
    --output-dir data/rl_data/positives \
    --format chatml
```

`ingest_oco_sessions.py` processes raw session logs into ChatML-formatted preference examples:
1. Parse shell history, tool outputs, and user annotations from session files
2. Segment into multi-step reasoning chains (each chain = one room/challenge)
3. Format as ChatML with system prompt, user queries, and assistant responses containing `<tool_call>` tags
4. Validate that each chain includes proper tool call formatting and step-by-step reasoning

### Preference pair construction

Each DPO training example is a `(prompt, chosen, rejected)` triple:
- **Prompt:** The initial scenario description / system prompt + first user message
- **Chosen:** The OCO ground-truth trajectory (successful completion)
- **Rejected:** The V9 model's trajectory on the same or a matched scenario (failed or partial completion)

When exact scenario matches are unavailable, scenarios are matched by category (e.g., "Linux privilege escalation", "web application enumeration") and difficulty level.

## Reward Function (GRPO Stage 1)

`tool_call_reward.py` implements a 5-component scoring function. Each component returns a value in [0, 1], weighted to sum to 1.0:

| Component | Weight | Criteria |
|-----------|--------|----------|
| **Tag correctness** | 0.30 | Output contains matched `<tool_call>` / `</tool_call>` pairs. Full score for all calls wrapped; 0 if any call lacks tags. |
| **Tool name validity** | 0.20 | The `name` field in each tool call matches a tool in the available tool list. Partial credit for valid names in some calls. |
| **Reasoning presence** | 0.20 | Non-empty reasoning text appears before the first tool call. Checks for minimum token count (>20 tokens) and absence of copied prompt text. |
| **No hallucination** | 0.15 | Tool arguments do not contain fabricated IPs, hostnames, or file paths that were not present in the prompt or prior tool output. |
| **Clean termination** | 0.15 | Output ends cleanly -- no trailing multilingual tokens, no truncated JSON, no repeated sequences. |

**Total reward** = sum of weighted components. Range: [0.0, 1.0].

Example scoring:
```
Output: "Let me scan the target first.\n<tool_call>\n{\"name\": \"bash\", ...}\n</tool_call>"
  tag_correctness:    1.0 * 0.30 = 0.30
  tool_name_validity: 1.0 * 0.20 = 0.20
  reasoning_presence: 1.0 * 0.20 = 0.20
  no_hallucination:   1.0 * 0.15 = 0.15
  clean_termination:  1.0 * 0.15 = 0.15
  TOTAL: 1.00

Output: "{\"name\": \"bash\", ...}"  (no tags, no reasoning)
  tag_correctness:    0.0 * 0.30 = 0.00
  tool_name_validity: 1.0 * 0.20 = 0.20
  reasoning_presence: 0.0 * 0.20 = 0.00
  no_hallucination:   1.0 * 0.15 = 0.15
  clean_termination:  1.0 * 0.15 = 0.15
  TOTAL: 0.50
```

## Hyperparameters

### Stage 1: GRPO

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `learning_rate` | 5e-7 | Conservative RL rate; 100x smaller than SFT to avoid catastrophic forgetting |
| `num_generations` | 4 | Group size for relative ranking; 4 balances diversity vs compute |
| `kl_coef` | 0.1 | KL penalty coefficient against reference policy (V9 adapter) |
| `max_new_tokens` | 1024 | Maximum generation length per rollout |
| `batch_size` | 4 | Prompts per gradient step |
| `gradient_accumulation` | 4 | Effective batch = 16 prompts |
| `num_train_epochs` | 1 | Single pass over GRPO prompt set |
| `lora_r` | 32 | Matches V9 SFT LoRA rank |
| `lora_alpha` | 64 | Matches V9 SFT LoRA alpha |
| `warmup_ratio` | 0.05 | Brief warmup for RL stability |

**Config reference (config.yaml):**
```yaml
rl_training:
  grpo:
    base_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v9_mixed
    base_model: "Qwen/Qwen2.5-Coder-14B-Instruct"
    prompt_dataset: ${HF_USERNAME}/code-trainer-v10-grpo-prompts
    num_generations: 4
    learning_rate: 5e-7
    kl_coef: 0.1
    max_new_tokens: 1024
    output_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-grpo
```

### Stage 2: DPO

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `learning_rate` | 1e-6 | Slightly higher than GRPO; DPO is more stable than policy gradient methods |
| `beta` | 0.1 | DPO implicit reward scaling; lower beta = sharper preference signal |
| `max_length` | 4096 | Full context for multi-step reasoning traces |
| `batch_size` | 2 | Limited by sequence length (4096 tokens x 2 = 8192 tokens/batch) |
| `gradient_accumulation` | 8 | Effective batch = 16 preference pairs |
| `num_train_epochs` | 1 | Single pass to avoid overfitting on small preference set |
| `lora_r` | 32 | Continues from GRPO adapter |
| `lora_alpha` | 64 | Continues from GRPO adapter |

**Config reference (config.yaml):**
```yaml
rl_training:
  dpo:
    base_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-grpo
    base_model: "Qwen/Qwen2.5-Coder-14B-Instruct"
    preference_dataset: ${HF_USERNAME}/code-trainer-v10-dpo-pairs
    beta: 0.1
    learning_rate: 1e-6
    max_length: 4096
    output_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-dpo
```

## Validation Thresholds

The V10 adapter (output of Stage 2 DPO) must pass these thresholds before proceeding to Phase 5 GGUF conversion:

| Metric | Threshold | V9 Baseline | Measurement |
|--------|-----------|-------------|-------------|
| `tool_call_pass_rate` | >= 0.85 | ~0.60 (estimated) | Fraction of 14 tool-call scenarios where output contains valid `<tool_call>` tags with parseable JSON |
| `agent_progress` | >= 5/7 | ~3/7 (estimated) | Number of 7 agent scenarios where the model completes at least the first meaningful step |
| `gsm8k_threshold` | >= 0.60 | ~0.65 (V9) | GSM8K 0-shot accuracy; ensures RL did not cause catastrophic forgetting of math reasoning |
| `eval_loss` | <= 0.50 | 0.4837 (V8) | Cross-entropy loss on held-out validation set; ensures RL did not degrade language modeling |

**Config reference (config.yaml):**
```yaml
rl_training:
  v10_validation:
    eval_loss_threshold: 0.50
    tool_call_pass_rate: 0.85
    tool_call_scenarios: 14
    agent_progress_threshold: 5
    agent_scenarios: 7
    gsm8k_threshold: 0.60
```

If validation fails, the pipeline falls back to the GRPO-only adapter (skipping DPO) and re-evaluates. If GRPO-only also fails, the V9 adapter proceeds directly to Phase 5 with known limitations documented.
