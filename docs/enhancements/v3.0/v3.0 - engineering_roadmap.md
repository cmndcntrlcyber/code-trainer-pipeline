## 1. Pipeline Overview

## 2. Mapping to Opus Mirror

The Opus Mirror document (`v3.0-opus-mirror.md`) provides a full decomposition of the Claude Opus training pipeline. The table below maps each Opus Mirror stage to its RTPI equivalent:

| # | Opus Mirror Stage | RTPI Phase | Code Path | Notes |
|---|-------------------|------------|-----------|-------|
| 1 | Transformer Architecture | N/A (use existing base) | -- | Qwen2.5-Coder-14B provides the architecture |
| 2 | Large-Scale Pretraining | Phase 3b: DAPT | `src/phase3b_dapt/` | Domain-adaptive continued pretraining on offsec corpus; not full pretraining |
| 3 | Constitutional Self-Critique (SFT) | Phase 4: SFT | `src/phase4_qwen_finetuning/` | Instruction tuning on curated mixed datasets (V7-V10) |
| 4 | RLAIF Reward Modeling | Phase 4e: RLAIF | `src/phase4e_rlaif/` | AI preference labeling + Bradley-Terry reward model on 1.5B |
| 5 | RL Fine-Tuning (PPO) | Phase 4f: PPO | `src/phase4f_ppo/` | PPO with learned reward model; KL-constrained against DPO checkpoint |
| 6 | Safety Eval & Deployment | Phase 5 + 5b | `src/phase5_deployment/`, `src/phase5b_abliteration/` | GGUF conversion, abliteration benchmarking, nexus-harness eval |
| -- | (no Opus equivalent) | Phase 4c: GRPO/DPO | `src/phase4c_rl/` | Chain-of-thought RL with rule-based reward; absent from Opus pipeline |

**Key differences from Opus Mirror:**
- RTPI operates on a 14B model with LoRA, not a frontier-scale model with full-weight training.
- Phase 3b (DAPT) is a lightweight domain adaptation step, not a trillion-token pretraining run.
- Phase 4c (GRPO/DPO) has no Opus equivalent -- it addresses tool-calling structural issues specific to our use case.
- Phase 5b (abliteration) is unique to RTPI -- it benchmarks refusal removal techniques for the offsec domain.

## 3. Phase 3b: Domain-Adaptive Continued Pretraining (DAPT)

### Purpose

Inject offensive security domain vocabulary, code patterns, and conceptual knowledge into the base model BEFORE instruction tuning. DAPT uses standard causal language modeling (next-token prediction) on raw text -- NOT instruction-formatted data -- so the model learns domain representations without being constrained by a specific response format.

### Corpus

| Source | Files | Size | Content |
|--------|-------|------|---------|
| Offsec code repositories | ~811K files | ~89 MB (core langs: Python, Go, C, Rust, Ruby, PowerShell, Bash, C#) | Exploit code, tooling, malware analysis, network protocols |
| PDF captures | ~60K captures | ~83 GB (rendered page images as source.txt) | Security research papers, CTF writeups, tool documentation, certification materials |
| Phase 1 source.txt captures | ~123K files | ~2 GB | Curated code samples from GitHub with quality filtering |

**Total estimated tokens:** ~150M tokens (after deduplication and filtering)

### Training Configuration

```yaml
dapt:
  base_model: "Qwen/Qwen2.5-Coder-14B-Instruct"
  corpus_dirs:
    - data/offensive-security/repositories
    - data/pdf_captures
  max_seq_length: 4096
  lora_r: 32
  lora_alpha: 64
  lora_dropout: 0.05
  learning_rate: 5e-5
  num_epochs: 1
  min_lines: 10
  max_lines: 1000
  output_adapter: ${HF_USERNAME}/qwen14b-dapt-offsec
```

**Key design decisions:**
- **LoRA-based, not full-weight:** Full continued pretraining of 14B parameters would require multi-GPU setups and risks catastrophic forgetting. LoRA r=32 adds ~67M trainable parameters (~0.5% of total), preserving the base model's general capabilities.
- **1 epoch only:** Domain pretraining is a light injection, not an exhaustive memorization. Multiple epochs on a small corpus risks overfitting to specific code patterns.
- **lr=5e-5:** Higher than SFT (1.5e-4) because DAPT operates on a different data distribution and needs to update representations more aggressively, but still conservative by pretraining standards.

### Validation

| Metric | Threshold | Measurement |
|--------|-----------|-------------|
| GSM8K accuracy | >= 0.55 | 0-shot; ensures math reasoning is preserved |
| Perplexity decrease | > 0% | Held-out offsec code perplexity should decrease vs base model |
| MMLU accuracy | >= 0.55 | Broad knowledge preservation check |

## 4. Phase 4e: RLAIF Reward Modeling

### Purpose

Train a scalar reward model that captures nuanced quality preferences beyond what rule-based rewards (Phase 4c) can express. The reward model encodes judgments about reasoning depth, tool-use appropriateness, output clarity, and security-domain correctness as a single score, which Phase 4f's PPO optimizer uses to refine the policy.

### AI Preference Labeling

For each prompt in the preference dataset:
1. Generate two candidate responses from the Phase 4c DPO checkpoint (temperature=0.8 and temperature=1.0)
2. Present both responses to a stronger model (the "judge") with a rubric covering:
   - Correctness of tool calls and reasoning
   - Quality of chain-of-thought explanations
   - Absence of hallucinated commands or IP addresses
   - Appropriate use of offensive security methodology (recon before exploit)
3. The judge produces a structured preference: `{chosen: "A" | "B", reasoning: "..."}` 
4. Pairs where the judge's reasoning is inconsistent or uncertain are discarded

**Position bias mitigation:** Each comparison is run in both orderings (A-first and B-first). Only pairs with consistent preferences across both orderings are retained.

### Bradley-Terry Reward Model

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Base model | Qwen2.5-Coder-1.5B-Instruct | Small enough to fit alongside the 14B policy model during PPO; large enough for meaningful reward signal |
| Architecture | Transformer + scalar head (replaces lm_head with Linear(d_model, 1)) | Standard reward model architecture |
| Training data | 8,000 preference pairs | Balance between data quality and A100 compute budget |
| Learning rate | 2e-5 | Standard for reward model training |
| Batch size | 16 | |
| Epochs | 3 | |
| Accuracy target | >= 75% | Agreement with held-out preference labels |

**Config reference (config.yaml):**
```yaml
rlaif:
  policy_model: "Qwen/Qwen2.5-Coder-14B-Instruct"
  policy_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-dpo
  reward_model_base: "Qwen/Qwen2.5-Coder-1.5B-Instruct"
  reward_model_output: ${HF_USERNAME}/code-trainer-reward-model
  preference_dataset: ${HF_USERNAME}/code-trainer-rlaif-preferences
  n_preference_pairs: 8000
```

### Reward Model Evaluation

Before proceeding to PPO, the reward model must pass:
- **Accuracy >= 75%** on held-out preference pairs
- **Calibration:** Predicted reward gap correlates with judge confidence
- **Robustness:** No systematic bias toward longer responses or specific formatting patterns

## 5. Phase 4f: RL Fine-Tuning (PPO)

### Purpose

Use the trained reward model to optimize the policy (14B + LoRA) through Proximal Policy Optimization. PPO provides continuous, gradient-based optimization against the learned reward signal, refining behaviors that DPO (discrete preference pairs) could not capture.

### Architecture

Three models must coexist during PPO training:

| Model | Size | Location | Purpose |
|-------|------|----------|---------|
| **Policy** (trainable) | 14B + LoRA (~67M trainable) | GPU (A100 80 GB) | The model being optimized |
| **Reward** | 1.5B | GPU (A100 80 GB) | Scores policy rollouts |
| **Reference** (frozen) | 14B (full weights) | CPU + offload | KL divergence anchor |

### VRAM Budget (A100 80 GB)

| Component | Estimated VRAM |
|-----------|---------------|
| Policy model (14B BF16 + LoRA) | ~28 GB |
| Reward model (1.5B BF16) | ~3 GB |
| KV cache + activations (policy) | ~6 GB |
| KV cache + activations (reward) | ~1 GB |
| Optimizer states (LoRA params only) | ~1 GB |
| Gradient checkpointing overhead | ~2 GB |
| **Subtotal GPU** | **~41 GB** |
| Reference model (CPU-offloaded) | 0 GB GPU / ~28 GB RAM |
| **Remaining GPU headroom** | **~39 GB** |

### Training Configuration

```yaml
ppo_training:
  policy_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-dpo
  base_model: "Qwen/Qwen2.5-Coder-14B-Instruct"
  reward_model: ${HF_USERNAME}/code-trainer-reward-model
  learning_rate: 1e-6
  kl_target: 0.05
  clip_range: 0.2
  batch_size: 4
  ppo_epochs: 2
  output_adapter: ${HF_USERNAME}/qwen14b-code-trainer-v10-ppo
```

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `learning_rate` | 1e-6 | Very conservative; PPO updates are high-variance and the policy is already strong from SFT+GRPO+DPO |
| `kl_target` | 0.05 | Adaptive KL coefficient target; keeps policy close to reference |
| `clip_range` | 0.2 | Standard PPO clip range; prevents excessively large policy updates |
| `batch_size` | 4 | Rollouts per step; limited by generation cost on 14B model |
| `ppo_epochs` | 2 | Optimization epochs per rollout batch; >2 risks overfitting to specific rollouts |

### Convergence Criteria

- **Reward trend:** Mean reward should increase monotonically over training
- **KL divergence:** Should remain within 2x of `kl_target` (adaptive coefficient adjusts)
- **Benchmark stability:** GSM8K >= 0.60, MMLU stable within 2 points of pre-PPO score
- **Reward hacking detection:** If reward increases but benchmark scores drop, training is stopped and rolled back to last stable checkpoint

## 6. Phased Timeline

| Weeks | Phase | Deliverable | Compute |
|-------|-------|-------------|---------|
| 1-4 | **V10 immediate** (Phase 4c) | GRPO + DPO adapters, V10 validation pass | A100-large, ~24h total |
| 5-8 | **DAPT** (Phase 3b) | Domain-adapted base adapter, perplexity validation | A100-large, ~10h |
| 9-12 | **RLAIF** (Phase 4e) | 8K preference pairs, trained reward model (accuracy >= 75%) | A100-large, ~4h training + judge inference |
| 13-16 | **PPO** (Phase 4f) | PPO-optimized adapter, final GGUF conversion | A100-large, ~10h |

**Critical path:** Weeks 1-4 (Phase 4c) are the immediate priority -- V9's tool_call failures block V10 deployment. DAPT (weeks 5-8) can be parallelized with V10 validation and abliteration benchmarking. RLAIF and PPO (weeks 9-16) are stretch goals that depend on Phase 4c producing a stable V10 adapter.

**Dependency chain:**
```
Phase 3b (DAPT) ─────────┐
                          v
Phase 4 (SFT on DAPT) ──> Phase 4c (GRPO/DPO) ──> Phase 4e (RLAIF) ──> Phase 4f (PPO) ──> Phase 5
                                                                                              |
Phase 5b (abliteration) <────────────────────────────────────────────────────────────────────────
```

Note: The current pipeline runs SFT directly on the base model (no DAPT). The DAPT adapter can be inserted retroactively -- Phase 4 SFT would be re-run on top of the DAPT adapter rather than the raw base model.

## Appendix A: Hardware Budget

### VRAM Estimates per Phase

| Phase | Operation | RTX 5060 Ti (16 GB) | A100 (80 GB) | Notes |
|-------|-----------|---------------------|--------------|-------|
| **3b: DAPT** | LoRA causal LM training | Not feasible | ~32 GB | 14B BF16 + LoRA + optimizer states |
| **4: SFT** | LoRA instruction tuning | Not feasible | ~34 GB | 14B BF16 + LoRA + seq_len=8192 |
| **4c: GRPO** | Generation (4x) + LoRA update | Not feasible | ~38 GB | 4 generations per prompt + KL against reference |
| **4c: DPO** | Preference optimization | Not feasible | ~34 GB | Similar to SFT with paired sequences |
| **4e: RLAIF** | Reward model training (1.5B) | ~8 GB (feasible) | ~6 GB | Small model; could train locally |
| **4e: RLAIF** | Preference generation (14B judge) | Not feasible | ~30 GB | 14B inference for labeling |
| **4f: PPO** | Policy + reward + reference | Not feasible | ~41 GB | See breakdown in Section 5 |
| **5: GGUF** | LoRA merge + quantize | Not feasible (RAM) | ~144 GB RAM | Needs A100-large for the 144 GB RAM, not GPU |
| **5b: Abliteration** | Activation caching + weight mod | Not feasible | ~35 GB | 14B BF16 + activation cache for 512 samples |
| **Inference** | GGUF Q5_K_M serving | ~11 GB (fits) | -- | Local llama.cpp/Ollama on 5060 Ti |
| **Inference** | GGUF Q4_K_M serving | ~9 GB (fits) | -- | More headroom for KV cache |

### Summary

- **All training runs on A100-large** (HF Jobs). The RTX 5060 Ti 16 GB cannot train a 14B model even with LoRA.
- **The 5060 Ti is for inference only** -- serving Q4_K_M or Q5_K_M GGUFs via llama.cpp or Ollama.
- **Exception:** The 1.5B reward model (Phase 4e) could be trained locally on the 5060 Ti if needed, though the A100 is faster and avoids context-switching.
