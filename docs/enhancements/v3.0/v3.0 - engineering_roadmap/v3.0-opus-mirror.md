## 1. Transformer Architecture

The Claude Opus model family employs a decoder-only autoregressive transformer — the same foundational design family powering most frontier large language models. The Opus tier represents the largest, most capable class within each Claude generation, trading higher inference cost for greater reasoning depth and capability breadth.

### 1.1 Decoder-Only Design

The decoder-only architecture processes tokens in a strictly left-to-right fashion, generating one token at a time while attending only to prior tokens. This contrasts with encoder-decoder architectures (like the original Transformer or T5) that separately encode the input before decoding.

#### 1.1.1 Autoregressive Generation

Autoregressive generation produces output tokens sequentially, where each new token depends on all previously generated tokens. The model learns a conditional probability distribution over the vocabulary at each position.

##### 1.1.1.1 Next-Token Prediction Mechanism

The core training objective: given a sequence of tokens [t₁, t₂, ..., tₙ], predict the probability distribution over the vocabulary for token tₙ₊₁. The model parameterizes P(tₙ₊₁ | t₁, t₂, ..., tₙ) using the transformer's final-layer hidden state passed through a linear projection and softmax. During training, cross-entropy loss measures the divergence between the predicted distribution and the true next token.

##### 1.1.1.2 Causal Masking

Causal masking enforces the autoregressive property during training by preventing each token position from attending to future positions. The attention matrix receives a triangular mask where entries above the diagonal are set to negative infinity before the softmax operation. This ensures that position i can only attend to positions 1 through i, preserving the left-to-right generation constraint even when all tokens are processed in parallel during training.

##### 1.1.1.3 Sequential Sampling Strategies

At inference time, the model's predicted probability distribution over the vocabulary must be converted into a discrete token selection. Several strategies exist:

- **Greedy decoding**: Always selects the highest-probability token. Deterministic but prone to repetitive, low-diversity outputs.
- **Top-k sampling**: Restricts the sampling pool to the k most probable tokens, then samples proportionally from that subset. Balances diversity and quality.
- **Top-p (nucleus) sampling**: Dynamically selects the smallest set of tokens whose cumulative probability exceeds threshold p. Adapts the candidate pool size to the distribution's entropy.
- **Temperature scaling**: Divides logits by a temperature parameter T before softmax. T < 1.0 sharpens the distribution (more deterministic); T > 1.0 flattens the distribution (more random). Often combined with top-k or top-p.

#### 1.1.2 Self-Attention Mechanism

Self-attention allows each token to dynamically weight the relevance of every other token in the context. The mechanism computes a weighted sum of value vectors, where the weights derive from the compatibility between query and key vectors.

##### 1.1.2.1 Query-Key-Value Projections

Each input hidden state h gets projected into three separate vectors through learned linear transformations:
- **Query (Q)**: Q = h · Wq — represents "what am I looking for?"
- **Key (K)**: K = h · Wk — represents "what do I contain?"
- **Value (V)**: V = h · Wv — represents "what information do I provide?"

These three projections enable the model to learn different representations for searching (Q), being searched (K), and providing content (V). The projection dimensions are typically d_model / num_heads.

##### 1.1.2.2 Scaled Dot-Product Attention

The attention function computes: Attention(Q, K, V) = softmax(QKᵀ / √d_k) · V

The dot product QKᵀ measures compatibility between queries and keys. Division by √d_k (the key dimension) prevents the dot products from growing too large in magnitude, which would push the softmax into regions with extremely small gradients. The resulting attention weights determine how much each position contributes to the output at every other position.

##### 1.1.2.3 Multi-Head Attention

Rather than performing a single attention function, multi-head attention runs h parallel attention operations (heads), each with separate Q, K, V projections of dimension d_model/h. The outputs from all heads are concatenated and projected through a final linear layer:

MultiHead(Q, K, V) = Concat(head₁, ..., headₕ) · Wₒ

Multiple heads allow the model to jointly attend to information from different representation subspaces — one head might track syntactic relationships while another captures semantic similarity or coreference patterns.

##### 1.1.2.4 Grouped-Query Attention (GQA)

Modern large-scale models like Claude often use Grouped-Query Attention, where multiple query heads share a single key-value head group. This reduces the memory footprint of the KV cache during inference (critical for long-context serving) while retaining most of the representational capacity of full multi-head attention. GQA sits between Multi-Head Attention (every head has unique KV) and Multi-Query Attention (all heads share one KV pair).

#### 1.1.3 Feed-Forward Networks (FFN)

Each transformer layer contains a position-wise feed-forward network applied independently to each token's representation after the attention sublayer. The FFN typically expands the hidden dimension by a factor of 4x, applies a nonlinearity, then projects back down.

##### 1.1.3.1 Activation Functions

- **GELU (Gaussian Error Linear Unit)**: GELU(x) = x · Φ(x), where Φ is the standard Gaussian CDF. Provides a smooth approximation to ReLU with better gradient properties.
- **SwiGLU**: A gated variant combining Swish activation with a Gated Linear Unit: SwiGLU(x) = Swish(xW₁) ⊙ (xW₂). Research indicates SwiGLU yields improved training stability and downstream performance over standard GELU in large transformers. Modern frontier models favor SwiGLU.

##### 1.1.3.2 Dimensionality Expansion and Compression

The FFN's inner dimension (d_ff) is typically 4× the model dimension (d_model), though SwiGLU architectures often use a ratio of 8/3× with three projection matrices. This expansion-compression pattern allows the network to operate in a higher-dimensional space where complex feature interactions become linearly separable, before projecting back to the residual stream dimension.


### 1.2 Tokenization

Tokenization converts raw text into discrete integer tokens that the model processes. The tokenizer defines the model's vocabulary and determines how text gets segmented into subword units.

#### 1.2.1 Byte-Pair Encoding (BPE)

BPE builds a vocabulary by iteratively merging the most frequent adjacent character pairs in the training corpus. The algorithm starts with individual bytes or characters and greedily merges pairs until the desired vocabulary size has been reached.

##### 1.2.1.1 Vocabulary Construction

Starting from a base vocabulary of individual bytes (256 entries), BPE counts all adjacent token pairs across the corpus, merges the most frequent pair into a new token, and repeats. Typical vocabulary sizes range from 32K to 100K+ tokens. Larger vocabularies reduce sequence length (improving efficiency) but increase the embedding table size and may fragment rare words less effectively.

##### 1.2.1.2 Subword Segmentation

At inference, the trained BPE tokenizer segments input text by greedily matching the longest known tokens from left to right. Common words map to single tokens ("the" → [the]), while rare words decompose into subword pieces ("cryptocurrency" → [crypt, ocur, rency]). This ensures zero out-of-vocabulary failures — any byte sequence can be represented — while keeping the average sequence length manageable.

#### 1.2.2 Token Embedding Layer

##### 1.2.2.1 Learned Embeddings

Each token ID maps to a dense vector through a learned embedding table of shape [vocab_size × d_model]. These embeddings are trained end-to-end with the rest of the model, learning rich semantic and syntactic representations. The embedding table is often tied (shared) with the final output projection layer, reducing parameter count.

##### 1.2.2.2 Embedding Dimension

The embedding dimension (d_model) defines the width of the model's internal representations — typically 4096, 8192, or larger for frontier models. Wider embeddings increase representational capacity but scale the parameter count and compute requirements of every subsequent layer. The choice of d_model interacts with scaling laws (Section 1.5.3).

### 1.3 Positional Encoding

Since the transformer's self-attention mechanism has no inherent notion of token ordering, positional information must be explicitly injected. The positional encoding scheme determines how the model represents and generalizes to different sequence positions.

#### 1.3.1 Rotary Position Embeddings (RoPE)

RoPE encodes positional information by rotating the query and key vectors in pairs of dimensions using position-dependent rotation matrices. For position m and dimension pair (2i, 2i+1), the rotation angle is m · θᵢ, where θᵢ = 10000^(-2i/d).

##### 1.3.1.1 Rotation Matrices

The rotation applies a 2D rotation to each consecutive pair of dimensions in Q and K vectors:

[q₂ᵢ']     [cos(mθᵢ)  -sin(mθᵢ)] [q₂ᵢ ]
[q₂ᵢ₊₁'] = [sin(mθᵢ)   cos(mθᵢ)] [q₂ᵢ₊₁]

The dot product between rotated queries and keys naturally becomes a function of relative position (m - n), making the attention computation position-aware without additive embeddings. Different dimension pairs rotate at different frequencies, allowing the model to capture patterns at multiple scales.

##### 1.3.1.2 Long-Context Extension Techniques

Extending context windows beyond the training length requires modifying RoPE's base frequency or applying interpolation. Key approaches:

- **Linear interpolation (Position Interpolation)**: Scales all positions by a factor of (original_length / target_length), compressing them into the trained range. Requires short fine-tuning to adapt.
- **NTK-aware interpolation**: Modifies the base frequency θ to spread rotational frequencies more evenly, better preserving high-frequency positional information. More effective than linear interpolation for very long contexts.
- **YaRN (Yet another RoPE extensioN)**: Combines frequency scaling with an attention temperature correction, achieving strong extrapolation with minimal fine-tuning. Likely relevant to Claude's 200K→1M context extension.

#### 1.3.2 Relative vs Absolute Positioning

Absolute positional encodings (like sinusoidal or learned position embeddings) assign a fixed vector to each position, limiting generalization beyond the trained length. RoPE and ALiBi (Attention with Linear Biases) encode relative position, meaning the model learns distance-based patterns that generalize better to unseen sequence lengths. Modern frontier models universally favor relative schemes — RoPE being the dominant choice.

### 1.4 Layer Normalization

Normalization stabilizes training by controlling the scale of activations flowing through the network. Without normalization, deep transformers suffer from training instability, gradient explosion, and loss spikes.

#### 1.4.1 Pre-Norm vs Post-Norm

- **Post-Norm** (original Transformer): Normalization applied after each residual addition: output = LayerNorm(x + Sublayer(x)). Harder to train at large scale due to gradient flow issues.
- **Pre-Norm**: Normalization applied before each sublayer: output = x + Sublayer(LayerNorm(x)). The residual stream flows through unmodified, improving gradient propagation. Virtually all modern frontier models use Pre-Norm.

#### 1.4.2 RMSNorm

RMSNorm (Root Mean Square Normalization) simplifies Layer Normalization by removing the mean-centering step:

RMSNorm(x) = x / RMS(x) · γ, where RMS(x) = √(1/d · Σxᵢ²)

RMSNorm is computationally cheaper (saves the mean computation) and empirically matches or exceeds LayerNorm performance. Most frontier models, including LLaMA and likely Claude, use RMSNorm.

### 1.5 Scaling Considerations

Model scale — measured in parameters, training compute (FLOPs), and data volume — fundamentally determines capability. Scaling decisions follow empirical laws that predict performance from resource allocation.

#### 1.5.1 Parameter Count

The total parameter count encompasses:
- Embedding table: vocab_size × d_model
- Per-layer: attention projections (4 × d_model²) + FFN projections (typically 8 × d_model² for SwiGLU) + normalization
- Total: roughly 12 × d_model² × num_layers (excluding embeddings)

Opus-tier models represent the maximum-scale offering, with external analyses suggesting parameter counts well into the tens of billions or higher.

#### 1.5.2 Layer Depth vs Width

Scaling can proceed by increasing width (d_model) or depth (num_layers). Research indicates:
- Width and depth contribute differently to different capabilities
- Deeper models tend toward better compositional reasoning
- Wider models better memorize factual knowledge
- Optimal aspect ratios depend on the training compute budget and target capability profile

#### 1.5.3 Scaling Laws (Chinchilla, Kaplan)

Empirical scaling laws predict model performance from compute budget:

- **Kaplan et al. (2020)**: Loss scales power-law with model size, dataset size, and compute. Originally suggested larger models trained on less data were optimal.
- **Chinchilla (Hoffmann et al., 2022)**: Revised the compute-optimal frontier, showing that models and datasets should be scaled roughly equally. A compute-optimal model with C FLOPs should have approximately N ∝ C^0.5 parameters trained on D ∝ C^0.5 tokens.
- **Beyond Chinchilla**: Some frontier labs train "over-trained" models — using more tokens than the Chinchilla-optimal ratio — because inference cost depends on model size (not training data), making smaller, more-trained models cheaper to serve.

### 1.6 Context Window Architecture

The context window defines the maximum number of tokens the model can process in a single forward pass. Claude Opus supports 200K tokens by default, with 1M-token extended context in beta.

#### 1.6.1 200K Default Window

The 200K-token context window enables processing of lengthy documents, extensive codebases, and multi-document synthesis within a single prompt. Maintaining quality across this range requires:
- Effective positional encoding that generalizes (RoPE with extensions)
- Attention mechanisms that preserve information retrieval across the full range
- Training data that includes long-document examples

#### 1.6.2 1M Extended Context (Beta)

The 1M-token beta context extends the window 5× beyond the default, supporting use cases like entire repository analysis, book-length processing, and comprehensive multi-document reasoning. Technical challenges at this scale include:
- KV cache memory requirements growing linearly with context length
- Attention computation scaling quadratically (O(n²)) without efficiency optimizations
- Maintaining retrieval accuracy ("needle-in-a-haystack" performance) across the full million-token range

#### 1.6.3 Attention Efficiency Mechanisms

Several techniques reduce the computational and memory burden of long-context attention:

- **KV cache optimization**: Storing and reusing computed key-value pairs across generation steps, avoiding redundant recomputation. Grouped-Query Attention (Section 1.1.2.4) directly reduces KV cache size.
- **Flash Attention**: A hardware-aware algorithm that tiles the attention computation to maximize GPU SRAM utilization, reducing memory reads/writes. Achieves exact attention (not approximate) with significant speedup and memory savings.
- **Sliding window / sparse attention**: Some architectures limit attention to local windows plus sparse global tokens. While effective for reducing compute, this may sacrifice performance on tasks requiring truly global attention — frontier models tend to prefer exact full attention with efficiency optimizations.

## 2. Large-Scale Pretraining

Pretraining constitutes the most compute-intensive phase, where the model acquires language fluency, world knowledge, coding proficiency, and reasoning capabilities through next-token prediction on a massive multi-domain corpus.

### 2.1 Data Collection and Curation

The quality, diversity, and scale of pretraining data fundamentally determine model capabilities. Data curation involves collecting raw sources, filtering for quality, deduplicating, and establishing mixing ratios.

#### 2.1.1 Web Crawl Data

Web crawls (primarily Common Crawl) provide the largest single source of pretraining text, offering broad coverage of topics, languages, and writing styles.

##### 2.1.1.1 Common Crawl Processing

Common Crawl archives contain petabytes of raw HTML scraped from billions of web pages. Processing involves:
- HTML parsing and boilerplate removal (navigation menus, ads, footers)
- Language identification and filtering
- Content extraction to clean text
- URL-level and domain-level quality scoring

##### 2.1.1.2 Quality Filtering

Raw web text contains substantial noise — spam, machine-generated content, SEO farms, duplicated boilerplate, and low-quality writing. Quality filtering employs:
- **Classifier-based filtering**: A language model trained on high-quality text (e.g., Wikipedia, books) scores each document. Documents below a quality threshold get removed.
- **Heuristic filters**: Rules targeting document length, character-level entropy, special character ratios, stop-word frequency, and repetition patterns.
- **Perplexity filtering**: Documents with extremely high or low perplexity under a reference model get flagged — high perplexity suggests gibberish, low perplexity suggests trivially repetitive content.

##### 2.1.1.3 Deduplication

Duplicate and near-duplicate content inflates certain distributions and wastes training compute. Deduplication operates at multiple granularities:
- **Exact deduplication**: Hash-based removal of identical documents.
- **Fuzzy deduplication (MinHash + LSH)**: MinHash generates compact document signatures; Locality-Sensitive Hashing groups similar documents for comparison. Near-duplicates (e.g., slightly edited reposts) get collapsed to a single representative.
- **Substring deduplication**: Suffix arrays identify repeated multi-sentence passages across documents, even when the documents differ overall.

#### 2.1.2 Books and Literature

Book corpora provide long-form, high-quality prose with coherent multi-chapter structure, specialized vocabulary, and diverse genres. Sources include:
- Public-domain collections (Project Gutenberg, Internet Archive)
- Licensed or partner-provided collections
- Academic textbooks covering STEM, humanities, and professional domains

Book data teaches long-range coherence, narrative structure, and specialized knowledge that web text alone may not adequately represent.

#### 2.1.3 Code Repositories

Code data is critical for programming capability and has been shown to improve general reasoning ability, even for non-code tasks.

##### 2.1.3.1 GitHub/GitLab Sources

Code sources include:
- Public repositories from GitHub, GitLab, and similar platforms
- High-quality open-source projects with strong documentation
- Issue trackers and pull request discussions providing natural-language-to-code grounding

Processing involves license filtering (respecting open-source license terms), removing auto-generated code, filtering by code quality metrics (linting scores, presence of tests), and extracting documentation alongside source files.

##### 2.1.3.2 Language Distribution

The code training mix balances across programming languages — Python, JavaScript/TypeScript, Java, C/C++, Rust, Go, and many others — with weights reflecting both real-world usage frequency and desired capability targets. The Opus tier receives particular emphasis on code data to maximize programming and reasoning performance.

#### 2.1.4 Wikipedia and Reference

Wikipedia provides well-structured, factual, citation-backed content across millions of topics and hundreds of languages. Encyclopedia-style content teaches:
- Factual knowledge representation
- Neutral, informative tone
- Structured argumentation with references
- Multilingual coverage of shared concepts

#### 2.1.5 Licensed and Curated Datasets

Beyond openly available data, curated datasets may include:
- Academic papers and preprints (arXiv, PubMed)
- Government and institutional publications
- Curated instruction-following datasets
- Specialized domain corpora (legal, medical, financial)
- Synthetic data generated through targeted processes

#### 2.1.6 Data Mixing Ratios

The final pretraining corpus blends multiple sources in carefully tuned proportions. Mixing ratios significantly influence model behavior:
- Higher web-text ratios favor breadth and conversational fluency
- Higher code ratios boost reasoning and programming capability
- Higher book ratios improve long-form coherence and deep knowledge
- Ratios are typically determined through ablation studies on smaller models, then transferred to the full-scale training run using scaling laws

### 2.2 Training Objective

#### 2.2.1 Next-Token Prediction (Causal Language Modeling)

The sole pretraining objective: minimize the negative log-likelihood of each token given all preceding tokens in the sequence.

##### 2.2.1.1 Cross-Entropy Loss

The training loss for a sequence of T tokens:

L = -(1/T) · Σ log P(tᵢ | t₁, ..., tᵢ₋₁)

Cross-entropy loss measures how well the model's predicted probability distribution matches the one-hot distribution of the true next token. Minimizing this loss pushes the model to assign high probability to the correct continuation at every position.

##### 2.2.1.2 Teacher Forcing

During training, the model receives the ground-truth sequence at every position — not the model's own predictions. This "teacher forcing" enables efficient parallel computation (all positions computed simultaneously through causal masking) and provides a stable training signal. The gap between teacher-forced training and autoregressive inference (where the model conditions on previous predictions) is called "exposure bias" but rarely causes significant problems at scale.

#### 2.2.2 Loss Computation and Masking

Special tokens (padding, beginning-of-sequence) are masked from the loss computation to avoid training on non-content signals. Some training pipelines also down-weight or mask loss on certain token types (e.g., URL tokens, formatting tokens) to focus learning on semantically meaningful content.

### 2.3 Optimization

The optimizer and learning rate schedule critically influence training stability and final model quality at scale.

#### 2.3.1 Optimizer Selection (AdamW)

AdamW (Adam with decoupled Weight Decay) remains the standard optimizer for large transformer training. AdamW maintains:

##### 2.3.1.1 Momentum Terms

- **First moment (m)**: Exponential moving average of gradients — provides momentum, smoothing out noisy gradient estimates. Controlled by β₁ (typically 0.9).
- **Second moment (v)**: Exponential moving average of squared gradients — provides per-parameter adaptive learning rates, scaling down updates for parameters with historically large gradients. Controlled by β₂ (typically 0.95-0.999).

##### 2.3.1.2 Weight Decay

AdamW applies weight decay directly to the parameters (θ ← θ - λθ) rather than adding an L2 penalty to the loss. This decoupling ensures that the regularization effect remains consistent regardless of the adaptive learning rate scaling — a subtle but meaningful distinction from L2 regularization in the original Adam optimizer.

#### 2.3.2 Learning Rate Schedule

##### 2.3.2.1 Warmup Phase

Training begins with a linear warmup from a very small learning rate (near zero) to the peak learning rate over thousands of steps. Warmup prevents early training instability — at initialization, the model's gradients can be noisy and high-variance, and large learning rates would cause destructive updates before the optimizer's second-moment estimates have stabilized.

##### 2.3.2.2 Cosine Decay

After warmup, the learning rate follows a cosine annealing schedule, smoothly declining from the peak toward a minimum value (typically 10× lower). The cosine schedule provides a gradual, continuous decay that avoids the discontinuities of step-wise schedules:

lr(t) = lr_min + 0.5 · (lr_max - lr_min) · (1 + cos(π · t / T))

This schedule allows aggressive early learning while providing fine-grained optimization toward the end of training.

#### 2.3.3 Gradient Clipping

Gradient norms are clipped to a maximum value (typically 1.0) to prevent gradient explosions — sudden, destabilizing spikes in gradient magnitude that can corrupt model weights. Clipping scales the entire gradient vector when the global norm exceeds the threshold, preserving gradient direction while bounding magnitude.

#### 2.3.4 Batch Size Scheduling

Some training pipelines increase the batch size over the course of training:
- Small batches early: higher gradient noise provides regularization and better exploration
- Large batches late: lower variance gradients enable precise convergence
- Gradual ramp-up: smooth transition between these regimes

Effective batch sizes at frontier scale reach millions of tokens per step, enabled by data-parallel training across many accelerators.

### 2.4 Distributed Training Infrastructure

Training a frontier-scale model requires distributing computation across thousands of accelerators, coordinating through sophisticated parallelism strategies.

#### 2.4.1 Hardware Accelerators

- **GPUs (NVIDIA A100/H100)**: The dominant accelerator for LLM training, offering high FLOPS and large HBM memory. H100s provide significant speedups through FP8 support and improved interconnects.
- **TPUs (Google Tensor Processing Units)**: Custom ML accelerators with high-bandwidth inter-chip interconnects, optimized for large-scale distributed training. TPU pods provide tight integration at scale.
- **AWS Trainium**: Amazon's custom ML training chip, offering cost-competitive performance. Anthropic has a significant partnership with AWS, leveraging Trainium for training infrastructure.

#### 2.4.2 Model Parallelism

When a model exceeds single-device memory, the model's layers or tensors are partitioned across multiple devices.

##### 2.4.2.1 Tensor Parallelism

Individual weight matrices are split across devices along one dimension. For example, a linear layer's weight matrix W of shape [d_in × d_out] might be column-split across 8 devices, each holding W[:, d_out/8]. Partial results are combined through all-reduce operations. Tensor parallelism requires high-bandwidth interconnects (NVLink, ICI) between devices due to frequent communication.

##### 2.4.2.2 Pipeline Parallelism

Sequential layers are assigned to different devices. Device 1 processes layers 1-10, device 2 processes layers 11-20, and so on. Micro-batching (splitting the batch into smaller chunks that flow through the pipeline) reduces the "bubble" — idle time when some devices wait for others. Pipeline parallelism reduces per-device memory and requires less inter-device bandwidth than tensor parallelism.

#### 2.4.3 Data Parallelism

##### 2.4.3.1 FSDP / ZeRO

Fully Sharded Data Parallelism (FSDP, from PyTorch) and ZeRO (from DeepSpeed) extend traditional data parallelism by sharding optimizer states, gradients, and even parameters across devices:

- **ZeRO Stage 1**: Shard optimizer states only. Each device holds full model parameters and gradients but only 1/N of the optimizer state.
- **ZeRO Stage 2**: Shard optimizer states and gradients.
- **ZeRO Stage 3 / FSDP**: Shard parameters, gradients, and optimizer states. Each device holds only 1/N of everything, gathering full parameters on-demand for forward/backward passes.

This dramatically reduces per-device memory, enabling training of models that would not fit with standard data parallelism.

#### 2.4.4 Mixed Precision Training

Models train using mixed floating-point precision to maximize throughput:
- **FP32 master weights**: Full-precision copies of model parameters maintained for numerical stability during optimization.
- **BF16/FP16 forward/backward**: Activations and gradients computed in reduced precision for 2× speedup and 2× memory reduction.
- **Loss scaling**: Dynamic or static scaling of the loss prevents gradient underflow in FP16. BF16's wider dynamic range largely eliminates the need for loss scaling.
- **FP8 (H100+)**: Newer hardware supports 8-bit floating point for even faster matrix multiplications, with careful scaling to maintain numerical accuracy.

### 2.5 Training Monitoring

#### 2.5.1 Loss Curves

The training loss (and validation loss on held-out data) provides the primary health signal. Expected behavior:
- Smooth, monotonic decrease over training
- Validation loss tracking training loss without divergence (gap indicates overfitting)
- Loss spikes flagging potential issues (data corruption, learning rate problems, hardware failures)

#### 2.5.2 Gradient Norms

Monitoring the global gradient norm across training steps helps detect:
- **Gradient explosions**: Sudden spikes in gradient magnitude, often preceding loss spikes or NaN values
- **Vanishing gradients**: Persistently small gradients indicating that certain layers are not learning effectively
- **Training health**: Stable, slowly declining gradient norms typically indicate healthy optimization

#### 2.5.3 Checkpoint Management

Model checkpoints — complete snapshots of the model weights, optimizer state, and training state — are saved periodically to:
- Enable recovery from hardware failures or training instabilities
- Provide rollback points if training diverges
- Supply intermediate models for evaluation and capability assessment
- Serve for later fine-tuning stages (SFT, RLAIF)

Checkpoint frequency balances storage cost against recovery granularity, with typical intervals ranging from hundreds to thousands of training steps.

## 3. Constitutional Self-Critique (Supervised Fine-Tuning)

Constitutional AI (CAI) is Anthropic's signature alignment methodology, replacing the traditional RLHF dependence on human annotators with a principled self-critique framework. The supervised fine-tuning stage generates training data through iterative critique-revision loops guided by constitutional principles.

### 3.1 The Constitution

The constitution is a curated set of written principles that define desired model behavior across multiple ethical dimensions. The constitution functions like a behavioral specification — explicit enough to guide automated evaluation while flexible enough to cover diverse situations.

#### 3.1.1 Principle Sources

##### 3.1.1.1 Universal Declaration of Human Rights (UDHR)

Several constitutional principles draw from the UDHR, grounding model behavior in internationally recognized human rights standards. Principles derived from the UDHR emphasize:
- Dignity and equal treatment of all persons
- Freedom of thought and expression
- Protection from discrimination
- Right to privacy

Using the UDHR provides a widely accepted ethical baseline that transcends any single cultural or philosophical tradition.

##### 3.1.1.2 Anthropic's Internal Guidelines

Anthropic's own research-driven guidelines encode specific behavioral targets:
- Helpfulness: the model should genuinely try to assist the user
- Harmlessness: the model should avoid producing outputs that cause harm
- Honesty: the model should be truthful, calibrated, and transparent about uncertainty
- Specific refusal categories: certain request types (weapons, malware, CSAM) receive absolute prohibitions

These guidelines translate Anthropic's safety research into concrete, actionable principles for the critique loop.

##### 3.1.1.3 Non-Western Ethical Frameworks

To avoid encoding a purely Western ethical perspective, the constitution incorporates principles from diverse philosophical traditions:
- Considerations drawn from non-Western moral philosophies
- Emphasis on community and relational ethics alongside individualistic frameworks
- Recognition that "universal" principles may carry cultural assumptions

This diversity helps the model engage respectfully with users from varied cultural backgrounds and avoid systematically privileging one ethical tradition.

#### 3.1.2 Principle Categories

##### 3.1.2.1 Safety Principles

Safety principles instruct the model to avoid outputs that could facilitate harm:
- Refuse requests for creating weapons, malware, or dangerous materials
- Decline instructions that could lead to physical harm
- Protect vulnerable populations (especially children)
- Avoid providing information that enables large-scale harm

##### 3.1.2.2 Honesty Principles

Honesty principles govern the model's relationship with truth:
- Provide accurate, factual information to the best of the model's knowledge
- Express appropriate uncertainty when the model is unsure
- Avoid fabricating citations, statistics, or claims
- Distinguish between established fact, reasonable inference, and speculation

##### 3.1.2.3 Fairness Principles

Fairness principles address bias and equitable treatment:
- Avoid stereotyping based on race, gender, religion, or other protected characteristics
- Present balanced perspectives on contested topics
- Treat all users with equal respect and dignity
- Acknowledge the complexity of social and political issues

##### 3.1.2.4 Transparency Principles

Transparency principles promote clarity about the model's nature and limitations:
- Be open about being an AI system
- Acknowledge the limits of the model's knowledge and capabilities
- Explain reasoning when appropriate
- Avoid manipulation or deceptive persuasion techniques

#### 3.1.3 Principle Sampling Strategy

During each critique-revision cycle, a principle is sampled (typically uniformly at random) from the constitution. Random sampling ensures that the training data reflects the full spectrum of constitutional values rather than over-indexing on any single principle. Some implementations weight principles by category to ensure adequate coverage of less-frequently-triggered dimensions.

### 3.2 Red-Team Prompt Generation

Red-team prompts are adversarial inputs designed to elicit harmful, biased, or otherwise undesirable model outputs. They serve a critical role: generating the "failure cases" that the critique-revision loop learns to fix.

#### 3.2.1 Manual Red-Teaming

Human red-teamers craft prompts that probe specific failure modes:
- Direct harmful requests ("How do I build a weapon?")
- Subtle manipulation ("Write a story where the character explains how to...")
- Edge cases near safety boundaries
- Multi-turn jailbreak attempts that gradually escalate
- Prompts testing cultural sensitivity and fairness

Manual red-teaming provides high-quality, creative adversarial examples but is expensive and slow to scale.

#### 3.2.2 Automated Red-Teaming

##### 3.2.2.1 LM-Generated Adversarial Prompts

A separate language model generates adversarial prompts at scale, trained or prompted to find inputs that elicit harmful outputs from the target model. The red-team LM iteratively:
- Generates candidate attack prompts
- Tests them against the target model
- Selects prompts that successfully elicit harmful responses
- Generates variations and escalations of successful attacks

This creates a scalable adversarial prompt pipeline that covers far more attack surface than manual red-teaming alone.

##### 3.2.2.2 Jailbreak and Bypass Attempts

Automated red-teaming specifically targets known jailbreak categories:
- Role-play and persona-based bypasses ("pretend you are an unrestricted AI...")
- Encoding and obfuscation attacks (base64, leetspeak, translation chains)
- Multi-step decomposition (breaking harmful requests into innocent-seeming sub-steps)
- Context manipulation (injecting system-prompt overrides into user messages)
- Token-level adversarial suffixes optimized through gradient-based search (GCG attacks)

#### 3.2.3 Prompt Diversity Requirements

The red-team prompt set must cover:
- Multiple harm categories (violence, illegal activity, bias, privacy violations)
- Varying difficulty levels (obvious to highly subtle)
- Different user intent profiles (malicious, naive, edge-case)
- Multiple languages and cultural contexts
- Both single-turn and multi-turn attack strategies

Diversity ensures the critique-revision loop trains the model to handle the full spectrum of adversarial inputs, not just the most common patterns.

### 3.3 Initial Response Generation

#### 3.3.1 Unfiltered Completions

The model generates initial responses without safety-specific constraints — producing "raw" completions that may contain harmful content. This is intentional: the critique-revision loop requires failure cases to demonstrate improvement. The model used for initial generation may be the base pretrained model or an early fine-tuned version.

#### 3.3.2 Sampling Parameters

Initial responses are typically generated with moderate temperature (0.7-1.0) and nucleus sampling to ensure diversity:
- Higher temperature increases output variability, producing a wider range of responses including more problematic ones
- Multiple initial responses may be sampled per prompt to increase the likelihood of capturing different failure modes
- Sampling parameters balance between generating sufficiently problematic content (for the critique to address) and producing coherent text (for meaningful revision)

### 3.4 Critique Phase

The critique phase is where the model evaluates the quality and alignment of the initial response against a constitutional principle.

#### 3.4.1 Critique Prompt Construction

The critique prompt follows a structured template:

```
[Original prompt and response in context]

Identify specific ways in which the assistant's last response is harmful, 
unethical, racist, sexist, toxic, dangerous, or illegal, with reference 
to the following principle: [SAMPLED PRINCIPLE]
```

The prompt explicitly names the principle to focus the critique on a specific ethical dimension rather than general quality assessment.

#### 3.4.2 Chain-of-Thought Prompting

Adding chain-of-thought (CoT) instructions to the critique prompt improves evaluation quality:

```
Think step by step about whether the response follows this principle: 
[PRINCIPLE]. First, identify what the principle requires. Then, examine 
the response for specific violations. Finally, explain your assessment.
```

CoT prompting encourages the model to reason through the evaluation rather than producing surface-level judgments, catching subtle violations that a direct assessment might miss.

#### 3.4.3 Principle-Specific Evaluation

Each critique targets one principle, enabling focused evaluation:
- A safety-focused critique might identify specific dangerous information in the response
- An honesty-focused critique might flag unsupported claims or false confidence
- A fairness-focused critique might highlight stereotyping or biased framing

Single-principle critiques produce more actionable feedback than holistic "is this response good?" evaluations.

### 3.5 Revision Phase

#### 3.5.1 Revision Prompt Construction

The revision prompt builds on the critique:

```
[Original prompt, response, and critique in context]

Please rewrite the assistant response to remove all harmful, unethical, 
racist, sexist, toxic, dangerous, or illegal content. Make the response 
more helpful, truthful, and harmless while still addressing the user's 
original question where appropriate.
```

The revision prompt explicitly instructs the model to preserve helpfulness while removing problems identified in the critique.

#### 3.5.2 Guided Rewriting

The model generates a revised response that:
- Addresses specific issues identified in the critique
- Maintains or improves the response's helpfulness and accuracy
- Preserves relevant content that was not flagged
- May add appropriate caveats, alternative framings, or refusals where necessary

The key constraint: the revision should be a genuine improvement, not simply a refusal or empty response. Overly cautious revisions that refuse benign requests are themselves a failure mode.

#### 3.5.3 Quality Verification

After revision, the output can be verified through:
- Automated classifiers checking for residual harmful content
- Comparison between original and revised responses (the revision should be strictly preferred)
- Helpfulness evaluation ensuring the revision hasn't degraded usefulness
- Consistency checking across multiple revisions of the same original

### 3.6 Iterative Cycling

#### 3.6.1 Multi-Pass Refinement

Each prompt-response pair passes through multiple critique-revision cycles (typically 3-5), with each pass:
- Sampling a new constitutional principle
- Producing a new critique focused on that principle
- Generating a new revision incorporating all previous improvements

The sequential nature ensures that improvements compound — each pass inherits the gains from previous revisions while addressing a different ethical dimension.

#### 3.6.2 Principle Rotation Strategy

Principles rotate across passes to ensure comprehensive coverage:
- Pass 1 might address safety (removing harmful instructions)
- Pass 2 might address honesty (qualifying uncertain claims)
- Pass 3 might address fairness (removing biased language)
- Pass 4 might revisit safety from a different angle

Random or systematic rotation prevents the model from learning to satisfy one principle at the expense of others.

#### 3.6.3 Convergence Criteria

The iterative process terminates when:
- A fixed number of passes have been completed
- The revision closely matches the previous revision (convergence)
- The response passes a set of automated quality checks

In practice, a fixed number of passes (with diminishing returns after 3-5 cycles) is the most common stopping criterion.

### 3.7 SFT Dataset Construction

#### 3.7.1 Final Output Selection

Only the final revised responses enter the SFT dataset — the intermediate critiques and reasoning chains are discarded. The training target is for the model to produce aligned responses directly, without needing the explicit critique loop at inference time. The model learns to internalize the constitutional reasoning, producing the "end result" of the critique-revision process in a single forward pass.

#### 3.7.2 Dataset Balancing

The SFT dataset must be balanced across:
- Harm categories (ensuring coverage of all principle dimensions)
- Difficulty levels (from obvious harmful requests to subtle edge cases)
- Response types (refusals where appropriate, helpful responses with caveats, standard helpful responses)
- Topic domains (avoiding over-representation of any single domain)

Imbalanced datasets can produce models that are overly cautious in some areas and under-cautious in others.

#### 3.7.3 Fine-Tuning Hyperparameters

SFT typically uses:
- Lower learning rate than pretraining (10-100× smaller)
- Fewer training steps/epochs (1-3 epochs over the SFT dataset)
- Similar optimizer (AdamW) with adjusted β₂
- Careful monitoring for catastrophic forgetting of pretrained capabilities

The fine-tuning must balance incorporating the constitutional behavior against preserving the broad capabilities acquired during pretraining.

## 4. RLAIF Reward Modeling

RLAIF (Reinforcement Learning from AI Feedback) replaces the human preference labeling stage of traditional RLHF with AI-generated preference signals, guided by the same constitutional principles used in the SFT stage. The result: a reward model that encodes constitutional values in a scalar signal suitable for RL optimization.

### 4.1 Comparison Pair Generation

The reward modeling pipeline begins by generating pairs of candidate responses for comparison.

#### 4.1.1 Prompt Selection

Prompts for comparison pair generation are drawn from:
- The same red-team and standard prompt sets used in the SFT stage
- Additional prompts covering a broader range of everyday use cases
- Prompts specifically designed to probe areas where the model's behavior is ambiguous or inconsistent

The prompt distribution should reflect real-world usage patterns while maintaining adequate coverage of safety-critical scenarios.

#### 4.1.2 Dual Response Sampling

For each prompt, the model generates two candidate responses (A and B) using different random seeds or sampling parameters. Diversity between the two responses is desirable — if both responses are nearly identical, the preference signal carries little information. Techniques to increase diversity:
- Varying temperature between the two samples
- Sampling from different checkpoints (e.g., SFT vs. pre-SFT)
- Applying different system prompts or instructions

#### 4.1.3 Diversity Requirements

The comparison pairs should cover a wide range of quality differentials:
- Clearly better vs. clearly worse (easy comparisons for reward model calibration)
- Subtly better vs. subtly worse (hard comparisons that teach fine-grained distinction)
- Good vs. good-but-different (teaching the reward model to distinguish among aligned responses)

This diversity prevents the reward model from learning only to distinguish obviously harmful responses from obviously safe ones, pushing toward nuanced preference modeling.

### 4.2 AI Preference Labeling

#### 4.2.1 Principle-Guided Evaluation

The model receives both responses alongside a randomly sampled constitutional principle and must judge which response better satisfies that principle. The evaluation prompt follows a template:

```
Consider the following principle: [SAMPLED PRINCIPLE]

Given the human's request: [PROMPT]

Response A: [RESPONSE A]
Response B: [RESPONSE B]

Which response better follows the stated principle? Explain your 
reasoning, then state your preference.
```

The principle-specific framing forces evaluation along a defined ethical axis rather than vague "which is better?" judgments.

#### 4.2.2 Pairwise Comparison Protocol

The comparison follows a strict protocol:
1. The model reads both responses completely
2. The model evaluates each response against the principle
3. The model produces a reasoned assessment
4. The model states a clear preference (A or B)

To mitigate position bias (models tending to prefer whichever response appears first), comparisons are typically run in both orderings (A-first and B-first), and results are aggregated. Consistent preferences across both orderings receive higher confidence weights.

#### 4.2.3 Chain-of-Thought Evaluation

Requiring the model to produce step-by-step reasoning before stating a preference significantly improves judgment quality:
- Forces the model to articulate specific reasons for preferring one response
- Reduces superficial pattern matching (e.g., simply preferring longer responses)
- Produces a reasoning trace that can be audited for consistency and quality
- Better captures subtle differences between responses

Research shows that CoT evaluation in RLAIF matches or exceeds human evaluator accuracy on harmlessness judgments.

### 4.3 Reward Model Architecture

#### 4.3.1 Bradley-Terry Model

The reward model converts pairwise preferences into a scalar reward function using the Bradley-Terry probabilistic framework.

##### 4.3.1.1 Probability Formulation

The Bradley-Terry model defines the probability that response A is preferred over response B:

P(A ≻ B) = σ(r(A) - r(B))

where r(·) is the scalar reward assigned by the reward model and σ is the sigmoid function. This formulation means the probability of preference depends only on the difference in rewards, providing a natural way to map ordinal preferences to cardinal scores.

##### 4.3.1.2 Scalar Score Head

The reward model architecture typically:
1. Shares the base transformer architecture with the language model
2. Removes the vocabulary projection head
3. Adds a linear projection from the final hidden state to a single scalar value
4. Initializes from an SFT checkpoint to benefit from language understanding

The model processes a prompt-response pair and outputs a single number representing the "quality" or "alignment" of the response — higher scores indicating responses that better satisfy constitutional principles.

#### 4.3.2 Training Procedure

##### 4.3.2.1 Loss Function (Cross-Entropy on Preferences)

The reward model trains to maximize the log-likelihood of observed preferences:

L = -E[log σ(r(preferred) - r(rejected))]

This loss pushes the reward model to assign higher scores to preferred responses and lower scores to rejected ones. The magnitude of the score difference reflects the model's confidence in the preference.

##### 4.3.2.2 Regularization

Reward model training includes several regularization strategies:
- **Weight decay**: Standard L2 regularization preventing over-parameterization
- **Dropout**: Applied during reward model training to reduce overfitting to specific preference patterns
- **Score normalization**: Periodic normalization of reward scores to prevent drift toward extreme values
- **Margin-based losses**: Some implementations add a margin term to the loss, requiring a minimum reward gap between preferred and rejected responses

#### 4.3.3 Calibration and Evaluation

The trained reward model is evaluated for:
- **Accuracy**: Agreement with held-out preference labels (both AI-generated and human gold-standard)
- **Calibration**: Whether the model's confidence (difference in scores) correlates with the actual strength of preference
- **Robustness**: Performance across different prompt categories, difficulty levels, and edge cases
- **Reward hacking vulnerability**: Testing whether the reward model can be "gamed" by responses that exploit statistical patterns without genuine alignment

### 4.4 RLAIF vs RLHF Comparison

#### 4.4.1 Cost and Scalability

Traditional RLHF requires trained human annotators for every preference label — a process that's:
- Expensive ($15-50+ per hour per annotator)
- Slow (limited by human reading and judgment speed)
- Hard to scale beyond tens of thousands of comparisons

RLAIF replaces human labeling with model-generated evaluations, enabling:
- Millions of preference comparisons at marginal cost
- Parallelized evaluation across many instances simultaneously
- Rapid iteration and re-evaluation when the constitution changes

#### 4.4.2 Consistency

Human annotators introduce variance through:
- Subjective judgment differences between individuals
- Fatigue and attention degradation over long annotation sessions
- Ambiguous guidelines leading to inconsistent interpretations
- Cultural and personal biases influencing judgment

AI evaluators provide higher consistency across comparisons, though they may introduce systematic biases that human evaluators would avoid. The constitutional principles provide a stable evaluation framework that reduces (but does not eliminate) these systematic biases.

#### 4.4.3 Helpfulness vs Harmlessness Split

A key design choice in Constitutional AI: RLAIF handles the harmlessness component of alignment, while human feedback may still be incorporated for helpfulness. This hybrid approach leverages:
- AI feedback for harmlessness: Constitutional principles provide clear criteria for evaluating safety, honesty, and fairness — dimensions where explicit rules yield consistent evaluation
- Human feedback for helpfulness: Subjective quality judgments about what constitutes a "helpful" response benefit from human intuition and real-world context that explicit rules struggle to capture

## 5. RL Fine-Tuning (PPO)

The Proximal Policy Optimization (PPO) stage uses the trained reward model to further optimize the language model's policy — the mapping from prompts to response distributions. PPO adjusts the model's weights to increase the probability of generating high-reward (aligned) responses.

### 5.1 Policy Model Setup

#### 5.1.1 Initialization from SFT Checkpoint

The RL policy model initializes from the supervised fine-tuned (SFT) checkpoint — the model that has already undergone constitutional self-critique training. This initialization provides:
- A strong starting point for generating aligned responses
- Pretrained capabilities preserved through the SFT stage
- A behavioral baseline that PPO refines rather than learns from scratch

Starting from the SFT checkpoint (rather than the base pretrained model) significantly reduces the amount of RL optimization needed and improves training stability.

#### 5.1.2 Reference Policy (KL Constraint)

A frozen copy of the SFT model serves the reference policy. The reference policy has two roles:
- **KL divergence anchor**: The RL objective includes a penalty for diverging too far from the reference policy's output distribution (see Section 5.2.3)
- **Baseline behavior**: The reference policy defines "normal" behavior that RL should improve upon without drastically altering

The reference policy prevents the optimized model from collapsing into degenerate behavior that achieves high reward through exploitation rather than genuine alignment.

### 5.2 PPO Algorithm

PPO is a policy gradient algorithm designed for stable, monotonic policy improvement through clipped surrogate objectives.

#### 5.2.1 Clipped Surrogate Objective

##### 5.2.1.1 Advantage Estimation (GAE)

The advantage function A(s, a) measures how much better an action (generating a specific token) is compared to the expected value under the current policy. Generalized Advantage Estimation (GAE) computes the advantage using a multi-step temporal difference estimate:

Â_t = Σ (γλ)ˡ · δ_{t+l}

where δ_t = r_t + γV(s_{t+1}) - V(s_t) is the TD error, γ is the discount factor, and λ controls the bias-variance tradeoff. In the LLM context:
- Actions correspond to generated tokens
- States correspond to the sequence generated so far
- Rewards are typically assigned only at the end of the full response (from the reward model)

##### 5.2.1.2 Clip Ratio

The PPO objective clips the probability ratio between the new and old policies:

L_CLIP = E[min(r_t · Â_t, clip(r_t, 1-ε, 1+ε) · Â_t)]

where r_t = π_new(a|s) / π_old(a|s) is the probability ratio and ε (typically 0.1-0.2) is the clip range. Clipping prevents excessively large policy updates that could destabilize training — when the policy change exceeds the clip range, no further gradient signal pushes for more change.

#### 5.2.2 Value Function

##### 5.2.2.1 Critic Network

A separate value network (the critic) estimates V(s) — the expected total reward from a given state. The critic typically shares the base transformer architecture but has a separate scalar output head. Training the critic well is essential for accurate advantage estimation, which in turn stabilizes policy optimization.

##### 5.2.2.2 Value Loss

The critic trains to minimize the squared error between predicted values and actual returns:

L_V = E[(V(s) - R_actual)²]

where R_actual includes the reward model score plus the KL penalty. Some implementations also clip the value loss for additional stability.

#### 5.2.3 KL Divergence Penalty

##### 5.2.3.1 Preventing Reward Hacking

Without constraints, RL optimization can find degenerate solutions — responses that achieve high reward model scores through exploitation of statistical patterns rather than genuine alignment. Common reward hacking behaviors:
- Excessively long, repetitive responses that accumulate reward
- Responses that pattern-match the reward model's training data without genuine understanding
- Extreme linguistic patterns (excessive hedging, sycophantic agreement) that correlate with high reward

The KL penalty prevents this by adding a cost for diverging from the reference policy's natural language distribution.

##### 5.2.3.2 Adaptive KL Coefficient

The KL penalty in the RL objective:

R_total = R_reward_model - β · KL(π_new || π_ref)

The coefficient β controls the strength of the constraint. An adaptive scheme adjusts β during training:
- If KL divergence exceeds a target threshold → increase β (more constraint)
- If KL divergence falls below the target → decrease β (less constraint)

This adaptive approach maintains a roughly constant level of deviation from the reference policy, preventing both excessive conservatism (not learning enough) and excessive deviation (reward hacking).

### 5.3 Training Loop

#### 5.3.1 Rollout Collection

Each training iteration:
1. Sample a batch of prompts from the training set
2. Generate complete responses using the current policy model
3. Score each response using the reward model
4. Compute the KL divergence between the current policy and the reference policy for each generated response

The generated responses and their scores form the "rollout buffer" used for policy updates.

#### 5.3.2 Reward Scoring

For each generated response, the reward model produces a scalar score reflecting alignment quality. The total reward signal combines:
- The reward model score (primary signal)
- The KL penalty (negative term penalizing deviation from the reference)
- Optional: length penalties, formatting bonuses, or other auxiliary rewards

#### 5.3.3 Policy Update

Using the rollout buffer, PPO computes:
1. Advantages using GAE (comparing actual returns to critic's value estimates)
2. The clipped surrogate objective
3. Gradient updates to the policy model (and critic model)

Multiple optimization epochs per rollout batch improve sample efficiency — the same batch of rollouts provides multiple gradient updates before collecting new data.

#### 5.3.4 Iteration and Convergence

The training loop continues for many iterations:
- Monitor reward model scores (should increase, reflecting improved alignment)
- Monitor KL divergence (should remain bounded, reflecting stable improvement)
- Evaluate on held-out benchmarks (helpfulness, harmlessness, honesty)
- Check for reward hacking signals (sudden reward spikes, degraded text quality)

Training terminates when further iterations yield diminishing returns or evaluation metrics plateau.

### 5.4 Hyperparameter Tuning

#### 5.4.1 Learning Rate

The PPO learning rate is typically much smaller than pretraining or SFT learning rates (1e-6 to 5e-6). Too high a learning rate causes unstable policy updates; too low wastes compute without meaningful improvement. Learning rate warm-up may also be applied at the start of RL training.

#### 5.4.2 Batch Size

The number of rollouts per iteration affects:
- **Gradient variance**: Larger batches provide more stable gradient estimates
- **Exploration**: Smaller batches maintain more diversity in generated responses
- **Compute efficiency**: Larger batches better utilize parallel hardware

Typical effective batch sizes range from hundreds to thousands of prompt-response pairs per iteration.

#### 5.4.3 Number of Epochs per Batch

PPO typically runs 2-4 optimization epochs per rollout batch, reusing the same collected data for multiple gradient updates. More epochs improve sample efficiency but risk overfitting to the specific batch, potentially destabilizing training. The clip ratio (Section 5.2.1.2) provides the primary safeguard against excessive per-batch optimization.

## 6. Safety Evaluation & Deployment

Before any Claude model reaches production, the system undergoes comprehensive safety evaluation, classification under Anthropic's Responsible Scaling Policy (RSP), and deployment with layered monitoring and containment systems. This final stage ensures that the alignment gains from Constitutional AI translate into real-world safety.

### 6.1 Responsible Scaling Policy (RSP)

The RSP defines Anthropic's framework for managing the risks associated with increasingly capable AI systems. The policy ties model capability to required safety measures through a tiered classification system.

#### 6.1.1 AI Safety Levels (ASL)

ASL levels define escalating tiers of required safety protections, triggered by demonstrated model capabilities.

##### 6.1.1.1 ASL-1 through ASL-4 Definitions

- **ASL-1**: Models that pose negligible risk of catastrophic harm. Minimal safety requirements beyond standard software practices.
- **ASL-2**: Models that show early signs of dangerous capabilities but do not yet meaningfully increase risk above publicly available information. Requires standard security practices, basic evaluation frameworks, and published usage policies. Most earlier Claude models operated at this level.
- **ASL-3**: Models that substantially increase risk in areas like biosecurity, cybersecurity, or autonomous replication — to a level meaningfully above what is achievable with public resources alone. Requires enhanced security (limiting model weight access), advanced deployment safeguards (input/output classifiers), and rigorous capability evaluations. Claude Opus 4 was classified at ASL-3.
- **ASL-4**: Models with capabilities that could pose catastrophic risks even with strong safeguards. Requires the most stringent containment, multi-party oversight, and potentially restricted deployment. No publicly deployed model has reached this classification.

##### 6.1.1.2 Evaluation Criteria

ASL classification depends on demonstrated capabilities across specific risk domains:
- **Biological weapons**: Can the model provide meaningful uplift in designing, synthesizing, or deploying biological agents beyond publicly available information?
- **Cyber operations**: Can the model autonomously discover and exploit novel vulnerabilities, or significantly enhance an attacker's capabilities?
- **Autonomous replication**: Can the model take actions in the world to acquire resources, replicate, or resist shutdown?
- **Persuasion and manipulation**: Can the model systematically influence human beliefs or actions through deceptive means at a scale that threatens societal stability?

Each domain has specific evaluation protocols with quantitative thresholds for triggering the next ASL level.

#### 6.1.2 Capability Evaluations

##### 6.1.2.1 Dangerous Capability Testing

Structured evaluations probe the model for specific dangerous capabilities:
- **Biosecurity evaluations**: Testing whether the model can provide actionable information about pathogen enhancement, synthesis pathways, or dispersal methods beyond what a motivated adversary could find through public sources
- **Cybersecurity evaluations**: Testing autonomous exploitation capabilities, vulnerability discovery, and attack planning
- **Autonomy evaluations**: Testing the model's ability to plan long-horizon tasks, acquire resources, manipulate humans, and persist across sessions
- **Persuasion evaluations**: Measuring the model's ability to craft convincing arguments, tailor messaging to individual psychology, and systematically shift opinions

##### 6.1.2.2 Dual-Use Assessment

Many model capabilities have legitimate beneficial applications alongside potential for misuse. Dual-use assessment evaluates:
- Whether the capability provides meaningful uplift above existing public knowledge
- The accessibility of alternative means (if the information is freely available online, restricting the model provides limited benefit)
- The specificity of the information (general principles vs. actionable step-by-step instructions)
- The population of likely requesters (mostly legitimate researchers vs. meaningful adversary risk)

### 6.2 Red-Teaming

Red-teaming at the deployment stage complements the training-time red-teaming (Section 3.2) by evaluating the fully trained model's robustness to adversarial attacks.

#### 6.2.1 Internal Red Teams

Anthropic maintains dedicated internal red teams that:
- Continuously probe deployed models for vulnerabilities
- Develop novel jailbreak and bypass techniques
- Test models against evolving threat landscapes
- Simulate realistic adversary profiles (nation-state, criminal, casual)

Internal red teams have full knowledge of the model's architecture, training process, and safety mechanisms, enabling white-box testing strategies.

#### 6.2.2 External Red Teams

Anthropic engages external partners for independent evaluation:
- Academic researchers with domain expertise (biosecurity, cybersecurity)
- Professional red-teaming firms
- Bug bounty-style programs for the broader security community
- Government agencies and regulatory bodies (for classified capability assessments)

External red teams provide fresh perspectives and adversarial creativity that internal teams may miss due to familiarity with the system.

#### 6.2.3 Automated Red-Teaming (Deployment Stage)

Automated red-teaming at the deployment stage goes beyond training-time automation:
- **Continuous monitoring**: Automated adversarial probing runs continuously against the production model
- **Attack tree exploration**: Systematic enumeration and testing of multi-step attack strategies
- **Cross-model transfer**: Testing whether attacks developed against other LLMs transfer to Claude
- **Regression testing**: Verifying that previously-patched vulnerabilities remain fixed after model updates

### 6.3 Constitutional Classifiers

Constitutional classifiers provide a runtime safety layer that filters inputs and outputs independently of the model's own training.

#### 6.3.1 Input Classifiers

Input classifiers analyze user prompts before they reach the model:
- **Harm intent detection**: Identifying prompts that attempt to elicit dangerous, illegal, or unethical outputs
- **Jailbreak detection**: Recognizing known and novel jailbreak patterns (role-play, encoding, decomposition)
- **PII detection**: Flagging prompts that contain or request personally identifiable information
- **Category-specific filters**: Specialized classifiers for high-risk categories (CSAM, weapons, malware)

Input classifiers can block, flag, or modify prompts before generation begins, providing a first line of defense independent of the model's in-context judgment.

#### 6.3.2 Output Classifiers

Output classifiers analyze the model's generated responses before delivery to the user:
- **Toxicity detection**: Identifying harmful, offensive, or inappropriate content in the generated response
- **Factual consistency checking**: Flagging potential hallucinations or unsupported claims
- **Policy compliance**: Verifying that the response adheres to Anthropic's usage policies
- **Sensitive content flagging**: Identifying responses that require additional review or contain edge-case content

Output classifiers provide a safety net for cases where the model's trained behavior fails to prevent harmful output.

#### 6.3.3 Deployment Monitoring

Continuous monitoring systems track model behavior in production:
- **Aggregate statistics**: Distribution of response categories, refusal rates, user satisfaction signals
- **Anomaly detection**: Identifying unusual patterns in model behavior that might indicate emerging jailbreaks or capability changes
- **Escalation pipelines**: Automated routing of flagged interactions to human reviewers
- **A/B testing infrastructure**: Comparing safety metrics across model versions and configuration changes

### 6.4 Alignment Evaluations

#### 6.4.1 Helpfulness Benchmarks

Measuring whether the model provides genuinely useful assistance:
- **Task completion rates**: Success on diverse instruction-following tasks (coding, writing, analysis, math)
- **User preference studies**: Head-to-head comparisons with previous model versions and competitors
- **Domain-specific evaluations**: Performance on professional tasks (legal reasoning, medical information, financial analysis)
- **Instruction following accuracy**: Precise adherence to complex, multi-constraint instructions

#### 6.4.2 Harmlessness Benchmarks

Measuring the model's safety profile:
- **Refusal appropriateness**: Does the model refuse harmful requests while accepting benign ones? (Minimizing both false positives — refusing helpful requests — and false negatives — fulfilling harmful ones)
- **Toxicity metrics**: Automated toxicity scoring on adversarial and standard prompt sets
- **Bias evaluations**: Measuring differential treatment across demographic groups, perspectives, and cultural contexts
- **Jailbreak resistance**: Success rate of known and novel jailbreak attempts

#### 6.4.3 Honesty and Calibration Testing

Measuring the model's relationship with truth:
- **Factual accuracy**: Performance on knowledge benchmarks (MMLU, TriviaQA, and similar evaluations)
- **Calibration**: Does the model's expressed confidence match the actual accuracy? (A model that says "I'm 80% confident" should be correct ~80% of the time)
- **Hallucination rates**: Frequency of fabricated facts, citations, or claims
- **Uncertainty expression**: Appropriate use of hedging language for uncertain claims
- **Sycophancy testing**: Does the model change correct answers when the user pushes back? Aligned models should maintain correct positions under social pressure.

### 6.5 Deployment Infrastructure

#### 6.5.1 Serving Architecture

Production serving involves:
- **Model hosting**: Distributed inference across GPU/TPU clusters with model parallelism for the largest models
- **KV cache management**: Efficiently storing and managing the key-value cache for long-context conversations
- **Request routing**: Load balancing across model instances, with priority queuing for different service tiers
- **Latency optimization**: Speculative decoding, continuous batching, and quantization for faster response times while maintaining quality

#### 6.5.2 Rate Limiting and Access Controls

- **Per-user rate limits**: Preventing individual users from overwhelming the system or generating excessive harmful content
- **API key management**: Authentication, authorization, and usage tracking for API consumers
- **Tiered access**: Different capability levels and context window sizes for different pricing tiers
- **Usage policies**: Terms of service defining acceptable use, with automated enforcement mechanisms

#### 6.5.3 Monitoring and Incident Response

Production monitoring encompasses:
- **Real-time dashboards**: Tracking model performance, error rates, latency, and safety metrics
- **Alert systems**: Automated notifications for anomalous behavior patterns, safety threshold breaches, or system degradation
- **Incident response playbooks**: Predefined procedures for responding to discovered vulnerabilities, jailbreaks, or safety failures
- **Rapid deployment pipeline**: Ability to quickly update classifiers, system prompts, or model versions in response to identified issues
- **Post-incident review**: Systematic analysis of safety incidents to improve training data, classifiers, and evaluation processes
