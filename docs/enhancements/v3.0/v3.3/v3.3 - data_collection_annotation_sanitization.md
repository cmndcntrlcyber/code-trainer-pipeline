# v3.3 Enhancement: Data Collection, Annotation & Sanitization Pipeline

**Project:** Code-Trainer / RTPI (Real-Time Pipeline Intelligence)  
**Target:** Multi-source data ingestion with automated annotation and full sanitization  
**Sources:** Local filesystem, Google Drive, OneDrive  
**Architecture:** Hybrid — standalone `src/phase1_cloud_ingestion/` with outputs feeding existing Phase 2  
**Estimated effort:** 9–12 days implementation, minimal HF Jobs cost (data pipeline only, no training)

---

## 1. Problem Statement

The Code-Trainer pipeline currently ingests data from GitHub repos (Phase 1/1c), local PDFs (Phase 1b), and Cloudflare R2 session logs. Three gaps limit training data quality and breadth:

### 1.1 No Cloud Drive Integration

Training-relevant files — security research docs, engagement reports, CTF writeups, code artifacts, and session logs — live on Google Drive and OneDrive but are inaccessible to the pipeline. Google Drive MCP tools exist at the Claude Code level but there is no standalone Python client for automated batch ingestion. OneDrive has zero integration.

### 1.2 No Unified Annotation Layer

`offsec_keywords.py` provides domain classification (13 offsec domains) and MITRE ATT&CK tactic mapping, but it is only called from the `offsec_scraper.py` GitHub scraping flow. PDF captures, R2 sessions, and any future cloud-sourced files receive no automated labeling. Quality scoring (`quality_scorer.py`) only applies to GitHub repos, not to documents or sessions.

### 1.3 No Dedicated Sanitization Module

PII and credential scrubbing is ad-hoc. `synthesize_offsec_tool_calls.py` (lines 642–663) has `SESSION_PATH_PATTERNS`, `REAL_DOMAIN_PATTERN`, and `OFFSEC_URL_PATTERN` regexes, but these only filter argument templates during synthetic data generation. There is no pipeline stage that scrubs PII, anonymizes real target hostnames/IPs/domains, or cleans up leaked credentials before data enters Phase 2 dataset builders.

Existing OCO session data (`data/oco_converted/train.jsonl`, 221 records) contains raw session content including real paths, hostnames, and potentially leaked credentials. This is a data hygiene risk for any model trained on this data.

### 2.2 Cloud File Navigator

The navigator is the pipeline entry point. It discovers files across all three sources, tracks sync state, and streams downloads into the annotation/sanitization pipeline.

**Discovery strategy per source:**

| Source | Discovery Method | Change Detection | Prioritization |
|--------|-----------------|-----------------|----------------|
| Local filesystem | `os.walk()` + extension allowlist | File `mtime` comparison | Newest-first within priority dirs |
| Google Drive | Drive API v3 `files.list()` with query filters; MCP fallback if API unavailable | `modifiedTime` per file_id | Shared → starred → recent |
| OneDrive | MS Graph API `/me/drive/root/children` recursive | `lastModifiedDateTime` per item_id | Specified folder paths → recent |

**Supported file types:** `.py`, `.go`, `.rs`, `.c`, `.cpp`, `.ps1`, `.sh`, `.md`, `.txt`, `.pdf`, `.json`, `.jsonl`, `.docx`, `.doc`

**Incremental sync model:** Each source tracks a high-water mark in `cloud_catalog.py`. On each run, only files modified since the last sync are re-downloaded and re-processed. SHA256 hash of file content is stored in the catalog; unchanged content is skipped even if metadata changed.

**Google Drive design decisions:**
- Primary path is Python API client (`google-api-python-client`) for standalone/automated execution via `sync_and_prepare.sh`
- MCP fallback (`mcp__claude_ai_Google_Drive__*` tools) for interactive ad-hoc use when API credentials are unavailable
- Google Docs/Sheets/Slides are exported as text via the Drive API `export()` endpoint
- `.docx` files are extracted via `python-docx`

**OneDrive design decisions:**
- MSAL device code flow for headless OAuth2 (no browser needed on training host)
- Token caching in `data/.onedrive_token_cache.json` (gitignored)
- Token refresh handled automatically by MSAL

### 2.3 Annotation Engine

Annotation runs on every file after download and before sanitization. It produces an `annotations.json` sidecar for each captured file.

**Annotation schema:**
```json
{
  "file_type": "code|document|session|report|config|unknown",
  "offsec_domain": "exploit|c2|recon|post_exploit|evasion|credential|payload|active_directory|cloud|network|malware|web_attack|mobile_iot|general",
  "offsec_domain_score": 0.85,
  "mitre_tactics": ["TA0001", "TA0002"],
  "mitre_techniques": ["T1059.001", "T1190"],
  "matched_keywords": ["sql-injection", "remote-code-execution"],
  "cve_references": ["CVE-2024-23897"],
  "quality_score": 72.5,
  "quality_components": {
    "content_depth": 18,
    "relevance": 16,
    "structure": 14,
    "completeness": 12,
    "actionability": 12.5
  },
  "language": "python",
  "estimated_tokens": 2048,
  "source_type": "google_drive|onedrive|local",
  "training_target": "dapt|sft|rl|skip"
}
```

**Integration with existing modules:**

- `domain_classifier.py` wraps `offsec_keywords.classify_offsec_domain()`, `extract_matched_keywords()`, `detect_cve_references()`, and `get_mitre_tactics()` from `src/phase1_data_collection/scrapers/offsec_keywords.py`. Extends them with a sliding-window approach (4KB windows with overlap) for long documents that exceed the keyword scanner's expected input size.

- `quality_scorer_docs.py` mirrors `quality_scorer.py`'s 5-component structure (20 pts each, total 0–100) but scored on document properties:
  - **Content depth** (20 pts): log-scale token count (20 pts at >2000 tokens)
  - **Relevance** (20 pts): offsec keyword density (20 pts at >5% match density)
  - **Structure** (20 pts): detected headings, sections, code blocks
  - **Completeness** (20 pts): not truncated, has conclusion/summary markers
  - **Actionability** (20 pts): contains commands, code snippets, step-by-step procedures

- `mitre_mapper.py` extends `MITRE_TACTIC_MAP` (currently tactic-level TA-codes only, in `offsec_keywords.py` line 275) with technique-level T-code mappings. Uses a static dictionary of technique keywords mapped to MITRE technique IDs.

- `file_type_classifier.py` uses extension + content heuristics (presence of `<tool_call>` tags → session, markdown headers → document, code syntax → code, etc.)

**Training target assignment:**
- `dapt`: code files with quality > 30 and offsec relevance (feeds `prepare_corpus.py`)
- `sft`: documents/reports with quality > 50 (feeds V10+ mixed dataset as Slice F)
- `rl`: session logs containing `<tool_call>` content (routed to `ingest_oco_sessions.py`)
- `skip`: low-quality, irrelevant, or duplicate files

### 2.4 Sanitization Pipeline

Sanitization runs after annotation, before files are written to the capture directory. All passes are idempotent and produce consistent replacements (same real value always maps to the same placeholder within a file).

#### Pass 1: PII Scrubber (`pii_scrubber.py`)

| Pattern | Replacement | Example |
|---------|-------------|---------|
| Email addresses | `user@redacted.example` | `john@company.com` → `user@redacted.example` |
| Phone numbers (US/intl) | `+1-555-0100` | `(555) 123-4567` → `+1-555-0100` |
| Usernames in paths | `/home/user/` | `/home/cmndcntrl/` → `/home/user/` |
| "Author: Name" patterns | `Author: [REDACTED]` | `Author: Jane Doe` → `Author: [REDACTED]` |
| SSN / credit card numbers | `[REDACTED]` | |

#### Pass 2: Target Anonymizer (`target_anonymizer.py`)

Absorbs and extends the existing regexes from `synthesize_offsec_tool_calls.py` (lines 642–663):

- **`REAL_DOMAIN_PATTERN`** — real company domains (starbucks, google, facebook, twitter, github.com, amazon, etc.) replaced with synthetic domains from a configurable pool (`target-01.example.com`, `app.target.htb`, `internal.corp.local`)
- **`SESSION_PATH_PATTERNS`** — session-specific paths (`.claude`, `claude-\d`, `/mnt/ssd/`, `scratchpad`, UUIDs, `kasm-user`, etc.) replaced with generic paths
- **Public IPs** — non-RFC 1918 IPs replaced with synthetic IPs from `10.10.10.0/24` or `10.129.0.0/16`
- **Preserves** lab/training ranges per config: `.htb`, `.thm`, `localhost`, `10.10.x.x`, `192.168.x.x`, `172.16.x.x`
- Builds a per-file replacement map so all references to the same real target are consistently replaced

#### Pass 3: Credential Scrubber (`credential_scrubber.py`)

| Pattern | Detection | Replacement |
|---------|-----------|-------------|
| API keys | `sk-...`, `ghp_...`, `AKIA...`, `Bearer ...` | `[API_KEY_REDACTED]` |
| Private keys | `-----BEGIN (RSA\|DSA\|EC\|OPENSSH) PRIVATE KEY-----` blocks | `[PRIVATE_KEY_REDACTED]` |
| .env values | `PASSWORD=...`, `SECRET=...`, `TOKEN=...` | `[ENV_VALUE_REDACTED]` |
| JWT tokens | `eyJ...` base64 header pattern | `[JWT_REDACTED]` |
| AWS credentials | `AKIA[A-Z0-9]{16}` | `[AWS_KEY_REDACTED]` |

#### Pass 4: Format Normalizer (`format_normalizer.py`)

- UTF-8 encoding normalization (fix mojibake, strip BOM)
- Line ending normalization (CRLF → LF)
- Trailing whitespace removal
- Maximum file size enforcement (100B – 500KB)
- SHA256-based content dedup against existing `data/captures/`, `data/pdf_captures/`, and `data/cloud_ingested/`

### 2.5 Capture Output Structure

Follows the existing Phase 1 SHA256 hash-based directory structure, directly compatible with `_iter_capture_dirs()` in `hf_dataset_converter.py`:

```
data/cloud_ingested/
  <2-char prefix>/
    <16-char sha256 hash>/
      source.txt              # sanitized content
      metadata.json           # source, path, size, timestamps, cloud IDs
      annotations.json        # offsec domain, quality, MITRE, training target
```

### 2.6 Phase 2 Integration

**Routing by `training_target` field:**

1. Files tagged `dapt` are symlinked/copied to `data/dapt_corpus/cloud_files/` and picked up by `prepare_corpus.py`'s file walker. Requires adding `data/dapt_corpus/cloud_files` to `corpus_dirs` in config.

2. Files tagged `sft` are converted to dataset records by a new `convert_cloud_captures_to_records()` function in `hf_dataset_converter.py`, added as **Slice F** ("cloud_docs") in the next mixed dataset builder.

3. Files tagged `rl` are copied to `data/cot_rl_sessions/cloud/` and processed by `ingest_oco_sessions.py` on the next sync run.

**sync_and_prepare.sh integration** — add between corpus refresh and R2 pull:

```bash

}
```

### SQLite schema extension

New `cloud_files` table in `catalog.db` (via `cloud_catalog.py`, following the `PDFCatalog` pattern from `src/phase1_pdf_ingestion/pdf_catalog.py`):

```sql
CREATE TABLE IF NOT EXISTS cloud_files (
    id              INTEGER PRIMARY KEY,
    content_hash    TEXT NOT NULL,
    original_hash   TEXT,
    source_type     TEXT NOT NULL,           -- 'local', 'google_drive', 'onedrive'
    source_id       TEXT,                    -- cloud file ID or local absolute path
    source_path     TEXT NOT NULL,           -- original filename / path in source
    capture_dir     TEXT,                    -- local capture directory path
    file_type       TEXT,                    -- 'code', 'document', 'session', 'report'
    language        TEXT,
    file_size       INTEGER,
    offsec_domain   TEXT,
    quality_score   REAL DEFAULT 0,
    training_target TEXT,                    -- 'dapt', 'sft', 'rl', 'skip'
    mitre_tactics   TEXT,                    -- comma-separated TA codes
    mitre_techniques TEXT,                   -- comma-separated T codes
    cve_references  TEXT,                    -- comma-separated CVE IDs
    source_modified TIMESTAMP,              -- mtime / modifiedTime from source
    ingested_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_annotated  TIMESTAMP,
    sanitized       BOOLEAN DEFAULT FALSE,
    processed       BOOLEAN DEFAULT FALSE,  -- routed to Phase 2
    UNIQUE(source_type, source_id)
);
CREATE INDEX IF NOT EXISTS idx_cloud_source  ON cloud_files(source_type);
CREATE INDEX IF NOT EXISTS idx_cloud_domain  ON cloud_files(offsec_domain);
CREATE INDEX IF NOT EXISTS idx_cloud_target  ON cloud_files(training_target);
CREATE INDEX IF NOT EXISTS idx_cloud_quality ON cloud_files(quality_score DESC);
CREATE INDEX IF NOT EXISTS idx_cloud_hash    ON cloud_files(content_hash);
```

## 8. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Google Drive API rate limiting (1000 queries/100s) | Medium | Low | Exponential backoff + batch listing with `fields` param to reduce calls |
| OneDrive device code flow UX friction | Medium | Low | Token caching with 90-day refresh; clear setup documentation |
| Over-sanitization (removing legitimate offsec content) | Medium | Medium | Preserve lab IP ranges and `.htb`/`.thm` domains; `--audit` flag logs all replacements for manual review |
| Under-sanitization (missing PII patterns) | Medium | High | Start with high-confidence regex patterns; audit mode before production use |
| Large file processing OOM | Low | Medium | Stream processing with file size cap (500KB); chunk long documents before annotation |
| Duplicate content across sources | Medium | Low | SHA256 content dedup at catalog level; cross-source dedup across all capture directories |
| Google Drive MCP unavailable in standalone mode | Medium | Medium | Primary path is Python API client; MCP is interactive fallback only |
| OneDrive personal vs work account confusion | Low | Low | Config specifies `tenant_id`; document which account type to use |
| Annotation quality drift on non-offsec files | Low | Medium | Sliding-window approach for long docs; quality thresholds are configurable per config |

## 10. Key Design Decisions

1. **Separate phase directory (`phase1_cloud_ingestion/`).** The existing Phase 1/1b/1c directories have tightly-coupled ingestion logic (GitHub API, Monaco Editor, PDF renderer). Cloud ingestion shares the output format but not the ingestion mechanism. A separate directory follows the project's one-directory-per-source pattern.

2. **Annotation as sidecar JSON.** Keeping annotations in `annotations.json` separate from `metadata.json` means the annotation engine can be re-run independently without re-downloading or re-processing source files.

3. **Sanitization before capture directory write.** Once a file lands in `data/cloud_ingested/`, it is safe to use. No downstream pipeline can accidentally consume unsanitized data.

4. **Google Drive API primary, MCP fallback.** The MCP tools require an active Claude Code session. The standalone Python pipeline runs via `sync_and_prepare.sh` on a timer without human interaction. The API client handles automated execution; MCP is available for interactive ad-hoc use.

5. **Device code flow for OneDrive.** The training host is headless. Device code flow is the standard OAuth2 pattern for headless clients connecting to Microsoft Graph. MSAL handles token caching and refresh automatically.

6. **Reuse SHA256 capture directory structure.** By producing the same `<hash2>/<hash>/source.txt + metadata.json` layout, cloud-ingested files work with `_iter_capture_dirs()` in `hf_dataset_converter.py` without modification.

7. **Retroactive sanitization as a separate script.** The existing 221 OCO sessions and 32K+ Phase 1 captures were never sanitized. `run_sanitize_existing.py` handles this as a one-time cleanup pass without modifying the core ingestion flow.
