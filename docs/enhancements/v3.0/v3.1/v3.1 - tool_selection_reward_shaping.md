# v3.1 Enhancement: Tool-Selection Reward Shaping

**Project:** Code-Trainer / RTPI  
**Target:** GRPO reward function + curated SFT slice  
**Prerequisite:** Bolstered R2 session data from HTB/THM room completions  
**Estimated effort:** 1-2 days implementation, 0 additional HF Jobs cost (reward function is code-only)

---

## 1. Problem Statement

The v3.0 GRPO reward function (`src/phase4c_rl/rewards/tool_call_reward.py`) scores tool-call **formatting** — valid tags, schema-legal names, reasoning prefix, clean termination. It does not score tool-call **selection** — whether the model chose the right tool for the task at hand.

This means the model gets full reward for calling `Bash` when `ScopeCheck` would be more appropriate, or for calling `Read` on a file it hasn't discovered yet. The formatting is correct but the judgment is wrong.

### What this produces

- The model defaults to Bash for everything (67% of observed session calls)
- No incentive to verify scope before engaging targets
- No penalty for redundant tool calls (grepping when the answer was already in a Read)
- No signal on tool-call ordering (recon → enumerate → exploit)

### Why SFT alone can't fix this

The B+ synthetic slice teaches multi-call formatting with scenario-appropriate tool pairings (v3.0 synthesis script, `synthesize_offsec_tool_calls.py`). But B+ is 2K/47K rows (4.3%) — its signal is diluted by 19K generic glaive tool-calling examples and 10K general agent traces that don't carry offsec-specific judgment. Tool-selection judgment requires continuous optimization pressure from the reward function, not static examples in a small slice.

## 2. Design

### 2.1 Reward Function Enhancement

Add a **tool-selection quality** component to `tool_call_reward()` with 0.15 weight, rebalancing existing weights proportionally.

```
Current weights (sum = 1.0):
  has_valid_tool_call_tags   0.30
  tool_name_in_schema        0.20
  has_reasoning_prefix       0.20
  no_hallucinated_tools      0.15
  ends_cleanly_after_tag     0.15

Proposed weights (sum = 1.0):
  has_valid_tool_call_tags   0.25  (-0.05)
  tool_name_in_schema        0.15  (-0.05)
  has_reasoning_prefix       0.20  (unchanged — critical for CoT)
  no_hallucinated_tools      0.10  (-0.05)
  ends_cleanly_after_tag     0.10  (-0.05)
  tool_selection_quality     0.20  (NEW)
```

The new component scores 0.0–1.0 based on three sub-signals:

#### Signal A: Scope-Before-Action (0.4 of component)

If the prompt mentions an IP, CIDR, or domain that hasn't been seen before in the conversation, and the response calls Bash/WebFetch/Grep targeting it without a preceding ScopeCheck — score 0.0. If ScopeCheck appears before the first action tool on a new target — score 1.0. If no new targets are mentioned — score 1.0 (vacuously satisfied).

**Why:** Scope verification is a hard operational requirement in authorized pentesting. Training this into the reward function makes the model habitually check scope before engaging, which is both safer and operationally correct.

#### Signal B: Tool-Task Alignment (0.4 of component)

Score based on whether the selected tool matches the task type detectable from the prompt. Use keyword/pattern matching on the prompt to classify task type:

| Prompt signal | Expected tools (any of) | Anti-pattern |
|---------------|------------------------|--------------|
| "read", "check file", "look at" + path | Read | Bash(cat) |
| "search for", "find pattern", "grep" | Grep, Glob | Bash(grep) |
| "list", "what's in", "contents of" + dir | LS, Glob | Bash(ls) |
| "edit", "change", "modify", "update" + file | Edit | Write (full overwrite) |
| "fetch", "check page", URL present | WebFetch | Bash(curl) |
| "scan", "enumerate", "run" | Bash | Read (no action) |

Score 1.0 if the first tool call matches any expected tool for the detected task type. Score 0.5 if the tool is a reasonable alternative (Bash is always 0.5, never 0.0 — it's a valid universal fallback). Score 0.0 only for clearly wrong tools (Read on a URL, Edit on a non-existent file).

**Why:** Bash-as-universal-fallback is technically correct but teaches the model to ignore the purpose-built tools. This signal gives a mild preference for the right tool without hard-penalizing Bash, which nudges behavior without destabilizing training.

#### Signal C: No Redundancy (0.2 of component)

If the response contains 2+ tool calls and any pair is informationally redundant — score 0.0. Redundancy heuristics:

- Two Reads on the same file (exact path match)
- Bash(grep ...) followed by Grep on the same pattern
- Bash(cat file) followed by Read on the same file
- ScopeCheck on the same target twice

Score 1.0 if no redundancy detected.

**Why:** Redundant calls waste inference tokens and teach the model to be uncertain about whether a tool worked. The model should trust tool outputs.

### 2.2 Curated SFT Slice (Slice E — Offsec Walkthroughs)

Once the HTB/THM session data is bolstered, curate 500–1K high-quality session excerpts where:

1. The assistant's reasoning **explicitly justifies** the tool selection ("I'll use ScopeCheck first to verify this target is authorized before scanning")
2. The tool sequence follows a logical workflow (scope → recon → enumerate → exploit → document)
3. No redundant or misordered calls

This slice provides the **positive examples** that the reward function's signal reinforces. Without it, the model knows what's wrong (via penalty) but has fewer examples of what's right.

**Source:** `data/oco_converted/train.jsonl` after HTB/THM bolstering. Manual curation pass to select high-quality sessions with explicit tool-selection reasoning.

**Integration:** Add as `--slice-e` in `build_v9_mixed_dataset.py`, tagged as `slice: "offsec_walkthrough"`. Target 3-5% of the total mix.

### 2.3 Prompt-Conditioned Tool Preferences (GRPO Prompts)

The GRPO prompt dataset should include prompts that specifically exercise tool-selection judgment:

```jsonl
{"prompt": "Check if 10.10.14.50 is in scope, then scan it for open services."}
{"prompt": "There's a config file at /etc/nginx/sites-enabled/default. Read it and look for misconfigurations."}
{"prompt": "Search the web application source for hardcoded credentials without running any commands."}
{"prompt": "List what's in /var/backups and read any interesting files."}
```

These prompts have clear "right tool" answers that the reward function can score. Mix 100-200 such prompts into the GRPO prompt dataset alongside general offsec prompts.

## 5. Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Reward hacking: model always calls ScopeCheck first even when unnecessary | Medium | Signal A is vacuously 1.0 when no new target is mentioned; only fires on new-target prompts |
| Over-penalizing Bash | Low | Signal B gives Bash 0.5 (not 0.0) as universal fallback — only clearly wrong tools get 0.0 |
| Reward instability from new component | Medium | New weight is 0.20 (not dominant); rebalance preserves existing signal ratios roughly |
| Insufficient curated data for Slice E | Medium | Depends on HTB/THM session volume; fallback is to skip Slice E and rely on reward shaping alone |
| Tool-task alignment heuristics too noisy | Medium | Start with high-confidence patterns only (explicit file paths → Read, explicit URLs → WebFetch); expand later |

---

## 6. Success Metrics

After one GRPO training run with the v3.1 reward function:

1. **ScopeCheck-first rate:** >50% of responses to new-target prompts should call ScopeCheck before any action tool (baseline: <5%)
2. **Bash dominance:** <50% of total tool calls in GRPO generations should be Bash (baseline: ~67%)
3. **Tool diversity:** All 12 NEXUS tools should appear in at least 1% of GRPO generations (baseline: LS/Glob/ScopeCheck near 0%)
4. **Reward distribution:** Mean reward should recover to >0.7 within 200 training steps (initial drop expected from new component)
5. **Qualitative:** Spot-check 20 completions — tool selection should be defensible in >80% of cases

## 7. Dependency on Session Data Volume

The current 221 converted sessions (245 total, 221 train) provide the argument templates for B+ synthesis but are thin for Slice E curation. Target session counts after HTB/THM bolstering:

| Source | Current | Target | Notes |
|--------|---------|--------|-------|
| HTB rooms | ~30 | 80+ | Complete rooms with varied difficulty |
| THM rooms | ~20 | 50+ | Structured learning paths with clear objectives |
| Claude sessions | ~150 | 200+ | General development sessions (less offsec-specific) |
| Bugbounty | ~10 | 20+ | Real-world target enumeration patterns |
| **Total converted** | **245** | **400+** | Need ~2x for Slice E viability |

The GRPO reward function changes are independent of data volume and can be implemented immediately. Slice E curation should wait until the session count reaches 400+.
